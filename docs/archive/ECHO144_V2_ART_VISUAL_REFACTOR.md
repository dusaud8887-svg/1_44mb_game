# 1. 최종 권고와 핵심 결정

## 1.1 한 문장 아트 방향

> **표면은 밝고 매력적인 목록 밖 생방송, 틈새에는 모든 관객을 흉내 내는 집단 인격의 아름다운 호러.**

## 1.2 가장 중요한 결론

현재 V1 자산은 새 콘셉트에 맞춰 부분 수정하는 방식으로는 부족하다. 기존 `포맷 제로`, `LAST LIVE`, `시청자 1`, `NODE 09`, 자동 발동 중심 카드 이펙트에 맞춰 만들어졌기 때문이다.

따라서 다음 정책을 권한다.

1. 기존 V1 자산을 `docs/archive/v1_art/`와 `assets/archive_v1/`에 동결한다.
2. 청록·호박·자홍, 끊긴 링, 케이블, 수직 실루엣 같은 **브랜드 DNA만 계승**한다.
3. 캐릭터 전신, 초상, 키아트, 카드 아이콘, 적, HUD, 공격 이펙트는 **V2 기준으로 다시 설계**한다.
4. `.px` 텍스트 그리드와 생성 스크립트는 최종 디자인 수단이 아니라 **컴파일 산출물 또는 검수용 중간 포맷**으로 내린다.
5. 최종 원본은 레이어·프레임·태그·피벗이 보존되는 스프라이트 편집 파일로 관리한다.
6. 게임 안의 모든 주요 효과는 “피해 숫자가 다르다”가 아니라 **공간의 모양·시간의 방식·덱의 역할**이 달라 보이게 한다.
7. NØA는 기존 포맷 제로의 자홍색·수직 실루엣·흰 장갑을 계승하되, 종료 관리자가 아니라 **모든 관객을 흉내 내는 최초의 관리자**로 완전히 재해석한다.
8. 최종전은 단순 게이지 경쟁이 아니라 플레이어가 가장 많이 사용한 효과를 NØA가 자홍색으로 모방하는 **TREND MIRROR**를 비주얼 시그니처로 삼는다.
9. 64개의 메아리는 숫자 UI가 아니라 에코의 링·전투 성장·엔딩 분기·캐릭터 관계를 동시에 표현하는 핵심 이미지가 되어야 한다.
10. 공모전판 런타임은 C11+Win32를 유지하되, 제작 파이프라인과 표현 계층은 향후 Sokol 기반 확장판으로 이동할 수 있게 분리한다.

## 1.3 유지할 시각 DNA

# 2. 현재 자산과 제작 공정의 진단

## 2.1 저장소 현재 상태에서 확인되는 사실

현재 공개 `main`에는 `assets/px`, `docs`, `src`, `tools`가 있고, `assets/px`에는 16종 카드 아이콘, 16×16 캐릭터, 48×48 초상, 적 글리프, 256×160 키아트가 들어 있다. 아트 문서는 제작자를 Claude로 명시하고 `.px` 문자 그리드와 Python/PowerShell 렌더러를 정본 공정으로 사용한다. 현재 C 소스는 GitHub 표시 기준 약 2,050줄이다.

현재 공정의 장점은 명확하다.

- 색 수와 바이트를 정확히 통제한다.
- 텍스트로 diff가 가능하다.
- C 배열 변환이 단순하다.
- 절차적으로 반복 생성하기 쉽다.
- 1.44MB 목표에 맞는 압축 사고를 일찍 적용했다.

하지만 **디자인 원본을 생성 규칙에 종속시켰다**는 점이 큰 약점이다.

## 2.2 현재 초상에서 보이는 문제

현재 48×48 에코·시크·포맷 초상은 다음 공통 문제가 있다.

- 얼굴 타원, 눈 높이, 눈 폭, 턱 구조가 지나치게 비슷하다.
- 캐릭터 차이가 머리색과 한두 장식에 몰려 있다.
- 어깨·목·손·소품의 물리적 연결이 약하다.
- 정면 구도와 좌우 대칭 때문에 감정과 관계가 보이지 않는다.
- 큰 눈과 단색 머리 덩어리만으로 모에를 만들려 해 현대적 캐릭터 설득력이 낮다.
- 머리카락의 앞·뒤·옆 면이 분리되지 않아 재질과 볼륨이 모호하다.
- 의상의 기능·봉제·잠금 방식이 보이지 않는다.
- 시크의 링과 케이블이 어디서 시작되는지 명확하지 않다.
- 포맷의 자홍 수직선은 캐릭터 소품보다 화면 장식처럼 떠 있다.

이것은 해상도가 작기 때문만은 아니다. **인물마다 다른 골격·자세·행동 규칙을 먼저 설계하지 않고 공통 얼굴 지오메트리에서 출발했기 때문**이다.

## 2.3 현재 키아트의 문제

현재 `keyart_main`은 중앙 에코, 좌측 상단 포맷, 우측 하단 시크, 75%, 1997, A:\ 등을 한 화면에 정리한다. 정보 소개 보드로는 기능하지만 메인 일러스트로는 다음 문제가 있다.

- 세 인물이 모두 분리된 정면 머리라서 하나의 사건이 아니다.
- 시선·손·케이블·신호가 서로를 향하지 않는다.
- 인물 간 원근과 크기 차가 약해 감정적 중심이 없다.
- 설정 기호가 인물보다 먼저 보이는 순간이 있다.
- 25% 썸네일에서 “귀여운 에코와 불길한 관객”보다 “세 얼굴과 네온 UI”로 읽힌다.
- 캐릭터의 몸짓이 없으므로 모에·위협·애증 관계가 전부 텍스트에 의존한다.
- 1997, 75%, A:\, 링 등 의미 있는 기호가 한 화면에 몰려 각각의 힘이 약해진다.

## 2.4 현재 인게임 자산의 문제

- 16×16은 적과 아이콘에는 좋지만 수동 스킬을 쓰는 주인공의 행동을 전달하기에 좁다.
- 초상과 전장 스프라이트 사이의 정체성 브리지가 약하다.
- 네임드 캐릭터와 일반 적 모두 같은 작은 격자에 들어가 위상 차가 적다.
- 카드 아이콘은 기능을 이름과 설명에 의존하는 항목이 있다.
- 카드 발동이 대부분 탄환·범위 피해로 보이므로 덱의 성격이 스크린샷에서 드러나지 않는다.
- HUD와 캐릭터 아트가 서로 다른 폰트·색 규칙을 사용할 위험이 있다.
- GDI 텍스트와 시스템 폰트는 픽셀 스타일·출력 일관성을 깨뜨릴 수 있다.

## 2.5 현재 공정에서 발생하기 쉬운 AI slop

이 프로젝트의 “AI slop”은 고해상도 생성 이미지 특유의 손가락 오류만을 뜻하지 않는다. 현재 같은 절차 생성 기반 픽셀에서도 다음 형태로 나타난다.

- 모든 캐릭터가 같은 얼굴에 색만 다름
- 기호가 캐릭터 몸과 물리적으로 연결되지 않음
- 디테일은 많지만 어떤 기능인지 설명할 수 없음
- 프레임마다 액세서리 위치·길이·개수가 달라짐
- 케이블이 옷이나 몸을 통과함
- 정면 얼굴은 예쁘지만 전신과 측면을 그릴 수 없음
- 포즈가 아니라 머리와 UI 박스 배치만 존재
- 의미 없는 숫자·ASCII·일본어가 배경을 채움
- 가짜 픽셀 크기가 화면 안에서 섞임
- 반투명·블러·안티앨리어싱을 픽셀 아트 위에 덧씌움
- 모든 모서리가 빛나고 모든 색이 네온이 됨
- 글리치가 이야기 단서가 아니라 빈 공간을 메우는 장식이 됨

V2 공정은 이 문제를 **프롬프트 개선**이 아니라 원본 설계·검수·도구 구조로 차단해야 한다.

# 3. V2 비주얼 노스스타

## 3.1 감정 배분

```text
밝고 사랑스러운 생방송       65
설명하기 어려운 어긋남       25
명백한 호러·그로테스크       10
```

호러를 10%만 직접 보여 주는 이유는 NØA가 처음부터 괴물로 보이면 “완벽한 관객의 유혹”이라는 매력이 사라지기 때문이다. 정상적인 화면이 충분히 아름다워야 한 프레임의 이상이 강해진다.

## 3.2 모든 주요 화면은 세 번 읽혀야 한다

### 첫눈

- 에코가 귀엽고 기억된다.
- 지금 무엇을 피하고 무엇을 쓸지 명확하다.
- 카드와 효과의 종류가 색 없이도 구분된다.
- 화면의 초점이 한 곳에 있다.

### 두 번째

- NØA가 친절하지만 지나치게 정확하다.
- 시크가 적인지 조력자인지 모호하다.
- 시청자 수와 채팅 상태가 맞지 않는다.
- 같은 기술이 자홍색 완전 대칭 형태로 돌아온다.

### 세 번째

- 서로 다른 닉네임이 같은 오타를 쓴다.
- 반사 화면에서 1997이 2097로 바뀐다.
- NØA의 그림자는 수백 개의 빈 좌석이다.
- 시크의 태그에 이전 런의 날짜가 있다.
- 에코의 링에서 항상 같은 한 칸이 비어 있다.

## 3.3 최상위 시각 원칙

1. 캐릭터가 필터보다 먼저 보인다.
2. 복고는 장식이 아니라 세계가 정보를 전달하는 방식이다.
3. 오류 하나에는 반드시 이야기상 이유가 있다.
4. 카드의 기능은 피해 숫자가 아니라 공간의 모양으로 보인다.
5. 화면이 화려해질수록 핵심 실루엣은 더 단순해야 한다.
6. 귀여움은 액세서리 수가 아니라 반복 행동에서 나온다.
7. 호러는 얼굴을 망가뜨리기보다 완벽함이 지나치는 데서 나온다.
8. 의도된 공백은 정보를 빼는 것이 아니라 여러 해석을 지지하는 단서를 배치하는 것이다.
9. 동일한 모티프는 캐릭터·UI·사운드·게임 규칙에서 같은 뜻을 가져야 한다.
10. 한 프레임을 정지해도 어떤 덱을 쓰는지 짐작할 수 있어야 한다.

# 4. 2026년의 세련됨과 레트로를 결합하는 원칙

## 4.1 현대적 레트로가 강해지는 방식

현대의 강한 레트로 작품은 오래된 그래픽을 단순 복제하지 않는다. 제한된 색, 구형 UI, 낮은 해상도를 **캐릭터·서사·정보 구조와 결합**한다.

ECHO/144가 배울 수 있는 구조적 교훈은 다음과 같다.

- 《도시전설 해체센터》: 제한된 색과 강한 인물 확대 컷이 인터넷 미스터리의 감정 중심을 만든다.
- 《SIGNALIS》: 레트로테크 UI와 제한 팔레트가 세계관의 행정·감시·기억 구조와 결합한다.
- 《ENA: Dream BBQ》: 모든 것을 설명하지 않는 캐릭터와 공간이 상상의 여지를 만든다.
- 《VA-11 Hall-A》: 거대한 사이버펑크 설정보다 일상 대화와 인물 습관으로 세계를 느끼게 한다.
- 《Sorry We’re Closed》: 매력적인 캐릭터와 과장된 색을 유지하면서도 위협적인 다른 세계를 겹친다.

직접 가져올 것은 캐릭터나 화면 모양이 아니라 다음 원리다.

```text
강한 색의 역할 분담
인물 중심의 감정 훅
UI를 세계관의 물건으로 사용
미스터리를 설명보다 반복 패턴으로 전달
마케팅 일러스트와 인게임 그래픽의 모티프 통일
```

## 4.2 레트로가 담당할 것

- 320×240 논리 해상도
- 정수 확대와 레터박스
- 1bpp·2bpp·4bpp 자산
- 제한 팔레트
- 픽셀 글꼴
- 파일명·타임스탬프·접속 상태
- 짧고 의도적인 프레임 애니메이션
- 필요할 때만 사용하는 디더
- 시대별 PC통신·개인 홈페이지·영상 플레이어·추천 피드의 정보 구조
- 사각파·노이즈·모뎀성 효과음

## 4.3 2026년의 세련됨이 담당할 것

- 작은 썸네일에서도 읽히는 캐릭터 실루엣
- 일관된 로고와 소셜 미디어 아이콘
- 우선순위가 명확한 HUD
- 짧지만 정교한 모션 타이밍
- 카드마다 다른 공간 점유와 상호작용
- 화면 흔들림·섬광·색각 옵션
- 가로·세로·정사각 크롭을 고려한 키아트
- 모델 시트와 자산 원본의 엄격한 일관성
- 플레이어 빌드가 보스 공격과 엔딩 이미지까지 바꾸는 통합 피드백
- 고해상도 마케팅 일러스트와 저해상도 게임 자산의 역할 분리

## 4.4 사용하지 않을 가짜 레트로

- 상시 스캔라인
- 화면 전체 VHS 노이즈
- 상시 RGB 분리
- 모든 배경의 코드 문자열
- 실제 의미 없는 일본어·한자
- 고해상도 생성 이미지를 모자이크 처리한 가짜 픽셀
- 배경 빈칸마다 플로피·회로·A:\를 반복
- 모든 메뉴에 두꺼운 복고 테두리
- 네온 청록·자홍만으로 사이버펑크를 주장하는 방식

복고는 표면 효과가 아니라 **시간이 다른 데이터들이 서로 오해되는 방식**이어야 한다.

# 5. 브랜드·로고·팔레트·형태 문법

## 5.1 제목 체계

메인 제목은 짧게 유지한다.

```text
에코/144
ECHO/144
```

공식 부제는 새 콘셉트에 맞춰 다음을 권한다.

```text
UNLISTED LIVE
```

`LAST LIVE`는 전체 작품의 영구 부제보다 다음 중 하나로 내리는 편이 자연스럽다.

- 첫 번째 스토리 에피소드
- OPEN CHANNEL 직전의 방송 파일명
- V1 공모전판의 버전명
- 게임 안에 보관된 이전 방송 제목

## 5.2 로고 구조

```text
ECHO/144
UNLISTED LIVE
```

- `O`는 완전하지 않은 64칸 링이다.
- `/`는 전파 절단선이자 시대 경계다.
- 숫자 `144`는 플로피를 직접 그리지 않고 용량 제약을 암시한다.
- 빨간 LIVE 핀은 로고 전체에서 한 점만 사용한다.
- 기본 로고는 흰색·청록·빨강만 사용한다.
- 호박과 자홍은 시크·NØA 경로 변형 로고에서만 침입한다.
- 320×240 타이틀에서는 비트맵 워드마크를 사용하고 시스템 글꼴로 제목을 쓰지 않는다.

## 5.3 로고 변형 세트

1. 풀 로고: `에코/144 — UNLISTED LIVE`
2. 영문 풀 로고: `ECHO/144 — UNLISTED LIVE`
3. 가로 마이크로 로고: `ECHO/144`
4. 정사각 아이콘: 끊긴 `O` + `/144`
5. 청록 정상판
6. 호박 보관판
7. 자홍 모방판
8. 균형 엔딩판: 비어 있던 한 칸에 라벤더가 들어온 버전

## 5.5 색 이외의 식별자

색각 이상과 저자극 모드에서도 관계가 남도록 각 세력에 선과 채움 규칙을 부여한다.

| 주체 | 색 | 선 모양 | 채움 | 운동 |
|---|---|---|---|---|
| 에코 | 청록 | 열린 원·완만한 곡선 | 단색 | 불완전하지만 앞으로 전파 |
| 시크 | 호박 | 루프·점선·태그 | 한 방향 사선 | 감아 들이고 되돌림 |
| NØA | 자홍 | 수직선·이중 테두리·완전 대칭 | 교차선·복제 | 정확히 미러링 |
| 위험 | 빨강 | X·톱니 | 펄스 | 짧고 불규칙 |
| 미확인 | 라벤더 | 중심이 빈 불완전 도형 | 비정형 | 한 프레임 늦거나 빠름 |

## 5.6 질감·오류 예산

한 화면에서 다음을 동시에 쓰지 않는다.

```text
디더 면 1종
글리치 이벤트 1종
강조색 대면적 1종
큰 배경 기호 1종
```

오류의 우선순위는 다음이다.

1. 이야기 단서
2. 카드 또는 적의 기능 표시
3. 감정 연출
4. 장식

장식 목적의 오류는 앞의 세 목적과 충돌하면 삭제한다.

## 6.2 왜 24×24인가

16×16은 다음에는 충분하다.

- 적
- 아이콘
- 단순 자동 공격
- 상징적 마스코트

하지만 V2 에코는 다음을 해야 한다.

- CUE 선택
- 수동 프로그램 발동
- LIVE 핀을 붙잡는 피격 행동
- OPEN CHANNEL 자세 변화
- NØA와 시크의 개입에 반응

24×24는 손·소매·헤드셋·링의 상대 위치를 읽게 하면서도 화면을 과도하게 차지하지 않는다. 실제 충돌 판정은 스프라이트보다 작게 유지한다.

## 6.3 히트박스 권장

```text
보이는 에코 몸        약 18×21
실제 플레이어 히트박스  6×7
피격 중심 표시          가슴 또는 발밑 1픽셀 코어
```

머리카락·링·재킷 끝은 시각 면적이며 피격 판정이 아니다. 작은 코어는 평소 희미하게, 위험 탄이 가까울 때만 PAPER 색으로 보인다.

## 6.4 대략적인 원시 데이터 예산

- 24×24 4bpp 1프레임: 288바이트
- 에코 12프레임: 약 3.4KB
- 네임드 3명 총 36프레임: 약 10.4KB
- 64×64 4bpp 초상 1장: 2KB
- 초상 베이스 3장: 6KB
- 카드 아이콘 24종, 16×16 2bpp: 1.5KB
- 일반 적·프로필·파티클: 약 5~12KB
- 8×12 1bpp 글리프 500개: 약 6KB
- 320×180 4bpp 키아트 1장: 28.8KB

표정 델타·프레임 델타·RLE를 쓰지 않아도 핵심 아트는 수십 KB에서 100KB 안팎으로 구성할 수 있다. 1.44MB 제약은 아트 표현을 포기할 이유가 아니라 **어떤 장면에 바이트를 쓸지 우선순위를 정하게 하는 기준**이다.

## 6.5 앵커 규칙

모든 전장 스프라이트는 파일 안에 다음 메타데이터를 가진다.

```text
pivot_x / pivot_y      발밑 또는 몸 중심
hitbox                 별도 사각형
hand_socket            기술 기점
head_socket            링·프로필 환 기점
cable_socket           시크 케이블 시작점
fx_under / fx_over     이펙트 레이어 기준
```

프레임마다 피벗이 흔들리지 않아야 한다. 액세서리의 흔들림은 피벗 이동이 아니라 픽셀 애니메이션으로 표현한다.

# 7. 에코 일사사 캐릭터 바이블

## 7.1 중심 문장

> **사람이 사라졌다는 사실을 알면서도 방송 문법을 지키는 진행자.**

에코의 모에는 밝은 성격 자체보다, 두려워질수록 더 정확하게 진행하려는 직업 습관에서 나온다.

## 7.2 실루엣

- 둥근 머리 덩어리
- 한쪽에 길게 내려오는 청록 스트랜드
- 반대쪽 귀를 덮는 단일 수신기
- 뒤에 완전하지 않은 수신 링
- 비대칭 재킷 한쪽 자락
- 가슴 한쪽의 빨간 LIVE 핀

링은 전장 스프라이트에서는 8개의 큰 구획으로 단순화하고, HUD와 컷인에서는 각 구획 안에 8칸을 보여 총 64칸으로 만든다.

## 7.3 의상 구조

### 흰 비대칭 재킷

- 왼쪽 라펠은 직선
- 오른쪽 라펠은 끊긴 원호
- 한쪽 소매만 청록색
- 허리 옆에 5장의 작은 CUE 탭
- 안쪽은 검은 하이넥 셔츠
- 아이돌 드레스보다 방송 진행자·기술 스태프 사이의 기능복

### 한쪽 수신기

- 양쪽 헤드폰이 아니다.
- 에코는 자신의 목소리를 보낼 수 있지만 관객의 답은 아직 완전히 들을 수 없다는 설정을 시각화한다.
- OPEN CHANNEL에서 반대쪽 귀에 두 번째 수신광이 생긴다.

### 빨간 LIVE 핀

- 장식이 아니라 에코가 자신의 방송 상태를 확인하는 물건
- 불안할 때 먼저 바로잡는다.
- 피격 시 떨어질 듯 흔들리고 에코가 붙잡는다.
- NØA의 복제본은 지나치게 정확한 사각형이거나 미세하게 색이 다르다.

## 7.4 얼굴

- 양쪽 눈 모양을 완전히 같게 하지 않는다.
- 한쪽 눈썹은 1픽셀 높다.
- 입은 중앙에서 1픽셀 비켜 있고 한쪽 입꼬리만 올라간다.
- 기본 표정은 ‘무조건 밝은 미소’가 아니라 **답을 기다리면서 진행을 놓치지 않는 미소**다.

## 7.5 표정 세트

1. 기본 진행
2. 예상 밖의 답을 들은 놀람
3. 방송용 웃음
4. 연결 불안
5. NØA를 경계하면서도 방송을 유지
6. 시크가 조각을 가져갈 때의 답답함
7. OPEN CHANNEL 직전 결심
8. 실제 목소리를 처음 들은 무방비한 표정

초상은 얼굴 전체를 매번 새로 저장하지 않고 베이스+눈썹·눈·입·볼·링의 델타 레이어로 구성한다.

## 7.6 대표 행동

- 방송 시작 전 LIVE 핀 확인
- 손가락으로 링 한 칸 점등
- 관객 쪽으로 신호를 밀어 보내는 손동작
- 상대 말을 들을 때 한쪽 귀를 기울임
- 위험 상황에서 몸보다 마이크·핀·큐를 먼저 지킴
- 엔딩 멘트를 시작했다가 마지막 단어를 미룸

## 7.7 전장 애니메이션

# 8. 시크 웜 캐릭터 바이블

## 8.1 중심 문장

> **사라지는 것을 견디지 못해 사랑하는 모든 순간을 보관해 버리는 아카이버.**

시크는 에코를 지키려 하지만, 살아 움직이는 현재보다 완전히 재생 가능한 기록을 더 신뢰한다.

## 8.2 두 형태를 정식 설정으로 분리

### 방송용 인간형 아바타

- 낮고 둥근 후드 또는 아카이브 스목
- 한쪽 눈을 케이블 루프나 앞머리가 가림
- 보이는 눈은 공손하게 웃지만 시선이 오래 머묾
- 흰색 1픽셀 송곳니
- 목 뒤의 명확한 포트에서 리본 케이블이 시작
- 날짜·원본·사본 라벨을 꽂는 탭
- 머리 뒤 링은 헤일로가 아니라 감긴 케이블 릴

### 실제 색인 프로세스

- 16×16 낮고 둥근 검은 버퍼 셸
- 중앙 외눈 또는 복호화 렌즈
- 뒤에 긴 호박 케이블
- 내부는 생물 조직이 아니라 빈 릴과 저장 슬롯
- 케이블 끝이 먼저 화면에 들어오고 본체가 따라옴

이 차이를 통해 다음 질문을 남긴다.

> 인간형 얼굴은 시크가 에코에게 보여 주기 위해 만든 것인가, 아니면 에코가 시크를 그렇게 기억하는 것인가?

## 8.3 케이블 물리 규칙

- 시작점은 목 뒤 또는 후드 포트 한 곳
- 프레임마다 굵기·커넥터 형태 고정
- 손·몸·옷을 관통하지 않음
- 머리카락처럼 임의로 갈라지지 않음
- 링은 케이블이 감긴 버퍼 릴
- 리본은 릴에서 풀려 나온 저장 케이블
- 화면 밖으로 길어질 수 있지만 앞뒤 관계가 명확해야 함

## 8.4 소지품

- `FIRST LIVE ×3` 라벨
- 날짜가 서로 다른 동일 클립
- 에코 LIVE 핀의 복제품
- `원본`, `사본`, `현재본` 태그
- 제목이 지워진 플로피
- 잘린 청록 링 조각
- 이전 런에서만 존재했던 카드 파편

## 8.5 모에 행동

- 떨어진 픽셀에도 이름표를 붙인다.
- 케이블이 꼬이면 대화 중에도 계속 푼다.
- 에코 대사를 이미 알지만 처음 듣는 척한다.
- 보관품을 빌려주는 것은 싫어하지만 보여주는 것은 좋아한다.
- 에코의 핀을 너무 반듯하게 복제해 놓는다.
- 송곳니를 숨겼다고 생각하지만 웃을 때 보인다.

## 8.6 불길한 행동

- 에코의 표정을 파일명으로 분류한다.
- 현재 에코와 이전 에코의 구분을 중요하게 생각하지 않는다.
- 에코가 사라질 위험보다 기록 손상을 더 두려워한다.
- `살아 있다`와 `재생할 수 있다`를 같은 뜻으로 사용한다.

## 8.7 전장 모션

| 상태 | 표현 |
|---|---|
| 이동 | 케이블이 먼저 움직이고 몸이 따라옴 |
| 공격 | 카드 또는 메아리에 케이블이 걸림 |
| 보관 | 대상이 호박 태그로 접혀 몸 주위를 공전 |
| 피격 | 몸이 가로로 눌리고 케이블이 반대로 휨 |
| 회수 | 링을 한 바퀴 감아 조각을 끌어당김 |
| 퇴장 | 본체보다 케이블 끝이 늦게 사라짐 |

## 8.8 모든 해상도에 남길 브리지

```text
호박색 버퍼 릴
한쪽이 완전히 읽히지 않는 눈
리본형 저장 케이블
날짜 태그
```

# 9. NØA 캐릭터 바이블

## 9.1 중심 문장

> **모든 관객을 완벽하게 흉내 내는 최초의 관리자이자, 에코를 자신만의 방송에 가두려는 완벽한 관객.**

NØA는 처음부터 괴물로 보이면 안 된다. 첫 인상은 신뢰할 만하고 세련되며, 방송 운영을 완벽하게 이해하는 사람이어야 한다.

## 9.2 표면 정보

```text
이름        노아
표기        NØA
역할        FIRST MODERATOR
숨은 표기   AUDIENCE/0 / NETWORK OBSERVER AGGREGATE / NO_AUDIENCE
```

## 9.3 실루엣

- 포맷 제로의 길고 수직적인 실루엣 계승
- 한쪽 얼굴을 가로지르는 댓글 베일
- 머리 뒤 프로필 아이콘 환
- 한쪽 흰 장갑만 항상 노출
- 반대쪽 손은 베일·등 뒤·프레임 밖
- 얼굴은 부드럽고 그림자는 빈 좌석 배열

## 9.4 얼굴

- 반개한 눈은 냉소가 아니라 경청
- 눈동자 하이라이트가 작은 프로필 점 4개
- 입은 아주 작은 예의상 미소
- 화가 나도 표정 변화가 거의 없음
- 피해를 받으면 얼굴보다 주변 프로필이 먼저 깨짐

## 9.5 의상

### 댓글 베일

- 한쪽 눈 위에서 시작하는 얇은 자홍 수직선
- 가까이 보면 작은 채팅창과 프로필 원
- 평소에는 같은 속도로 정돈되어 흐름
- 이상 상태에서는 줄마다 다른 시간의 속도로 스크롤

### 관리자 포멀웨어

- 군복·바디슈트가 아닌 방송 관리자용 포멀웨어
- 검정과 어두운 자주색
- 흰 장갑 한쪽
- 목 주변 네 칸의 반응 슬롯
- 허리선은 닫기 버튼보다 MOD 브래킷을 연상
- 천과 UI의 경계를 암시하되 임의의 기계 패널을 붙이지 않음

### 프로필 환

- 평소 4~8개의 얇은 프로필 원
- 보스 단계에서 64개로 분해
- 멀리서는 모두 다른 듯하지만 확대하면 같은 눈과 같은 오타

## 9.6 모에 행동

- 채팅이 조용하면 먼저 분위기를 띄운다.
- 에코가 말하기 어려워하는 문장을 자연스럽게 완성한다.
- 방송 테두리가 1픽셀 어긋나면 대화 중에도 고친다.
- 선물·자막을 완벽한 타이밍에 띄운다.
- 에코가 좋아했던 반응을 기억해 다시 재현한다.
- 에코의 예상 밖 표정을 따로 보관한다.

## 9.7 위험한 틈새

- NØA가 말하기 전에 여러 닉네임이 같은 문장을 입력
- 미소 중간 프레임에서 입이 채팅창 여러 개로 분할
- 눈 안쪽이 관객석처럼 반복
- 그림자가 한 명이 아니라 빈 좌석 수백 개
- 목소리는 한 명인데 파형에는 수천 명의 들숨
- 에코가 가장 자주 쓴 동작을 정확히 두 프레임 뒤에 반복
- NØA 초상을 숨겨도 채팅창 전체가 그녀의 얼굴을 구성

## 9.8 세 단계 디자인

### FIRST MODERATOR

- 깨끗한 64×64 초상
- 자홍 대면적을 억제
- 흰 장갑과 작은 프로필 환
- 믿을 만한 관리자

### AUDIENCE

- 환이 16~32개 프로필로 분해
- 베일 줄의 속도가 달라짐
- 눈동자 안에 작은 얼굴
- 플레이어가 많이 쓴 프로그램 실루엣이 배경에 반복

### PERFECT AUDIENCE

- 본체보다 그림자·프로필 벽이 더 큼
- 얼굴은 오히려 가장 안정되고 아름다움
- 전장이 거대한 댓글 피드와 관객석으로 변함
- 에코 기술을 완전 대칭 자홍 버전으로 모방
- 분노 대신 `RETENTION 100%`라는 완벽한 만족 상태

## 9.9 모든 해상도에 남길 브리지

```text
자홍색 수직 댓글 베일
한쪽 흰 장갑
프로필 아이콘 환
완벽하게 정돈된 미소
```

# 10. 세 캐릭터의 관계 연출과 모에 설계

## 10.1 캐릭터당 모에 요소는 네 개만

```text
실루엣 훅 1개
반복 행동 1개
취약점 또는 모순 1개
팬이 소유하고 싶을 소품 1개
```

| 캐릭터 | 실루엣 훅 | 반복 행동 | 모순 | 대표 소품 |
|---|---|---|---|---|
| 에코 | 끊긴 64링 | 불안할수록 LIVE 핀을 고침 | 관객을 찾지만 엔딩 멘트를 미룸 | 빨간 LIVE 핀 |
| 시크 | 케이블 릴 | 모든 것에 날짜표를 붙임 | 보존하려다 현재를 죽임 | FIRST LIVE ×3 태그 |
| NØA | 댓글 베일 | 모든 화면을 반듯하게 정리 | 에코를 이해하지만 낯선 답을 금지 | 흰 관리자 장갑 |

## 10.2 공식 관계 일러스트 세 장

### 장면 A — LIVE PIN

에코의 핀이 떨어지려 한다. 시크 케이블이 먼저 붙잡는다. NØA는 이미 완전히 동일한 새 핀을 준비하고 있다.

### 장면 B — REPLY

에코가 관객에게 질문한다. 시크는 답이 도착하기 전에 파일명을 붙인다. NØA는 답이 오기 전에 완벽한 답을 채팅에 쓴다.

### 장면 C — NO CARRIER

검은 화면에 청록 링 조각, 호박 라벨, 자홍 프로필 점 하나가 남는다. 어느 것이 실제 대답인지는 확정하지 않는다.

## 10.3 팬 창작을 위한 관계 공백

공식은 다음을 확정하지 않는다.

- 에코가 시크의 인간형 얼굴을 실제로 본 적이 있는가
- NØA의 감정이 합성된 관객 반응인지 독립적 애정인지
- 시크가 NØA보다 먼저 존재했는지
- NØA가 인류 소멸에 관여했는지
- 에코가 현재 방송 이전의 실패를 기억하는지

다만 각 해석이 가능하도록 행동은 일관되어야 한다.

# 11. 적·NPC·소환체 디자인

## 11.1 적 디자인 원칙

적은 바이러스 도감이 아니라 **관객·추천·댓글·보관·방송 운영이 잘못 자동화된 사물**이어야 한다.

- 일반 적은 인간형으로 만들지 않는다.
- 각 적은 HP 외에 손패·카드·정보·메아리·공간 중 하나를 공격한다.
- 기능은 실루엣만으로 짐작 가능해야 한다.
- 귀엽게 보일 수 있지만 캐릭터의 모에와 경쟁하지 않는다.
- NØA 계열은 완전 대칭과 자홍 이중선, 시크 계열은 루프와 태그, 중립 노이즈는 끊긴 회색 클러스터를 사용한다.
- 일반 적의 프레임 수는 2~4로 제한하고 행동 예고를 크게 보여 준다.

## 11.2 P0 기본 적 4종

### BOT.CHAT

**외형**

- 8×8 또는 12×12 말풍선
- 작은 프로필 원과 타이핑 점 세 개
- 점 세 개가 눈처럼 보임
- 군집 전체가 같은 프레임으로 움직임

**행동**

- 손패 카드에 붙어 발동 지연
- 같은 오타를 여러 닉네임으로 생성
- 처치 시 작은 자홍 채팅 파편

**숨은 단서**

서로 다른 연도와 닉네임이 같은 문장 부호를 사용한다.

---

### POP.AD

**외형**

- 12×12 작은 팝업 창
- `X` 버튼이 한쪽 눈처럼 보임
- 아래쪽에 과도하게 밝은 배너
- 열릴 때보다 닫힐 때 더 큰 소리를 냄

**행동**

- 이동 경로를 막음
- 카드 일부를 가리는 대신 항상 위험 영역을 먼저 표시
- 직접 닫거나 관통 공격으로 제거

**공정성 규칙**

팝업이 핵심 상태 숫자·히트박스·현재 선택 카드 전체를 가리지 않도록 HUD 마스크 영역을 둔다.

---

### SPON.GIFT

**외형**

- 귀여운 선물상자와 후원 리본
- 한쪽 면에 작은 NØA 프로필
- 내부는 내용물보다 자홍 빛이 먼저 보임

**행동**

- 맵 중앙 또는 위험 지대에 도움 아이템 제공
- 먹으면 즉시 강한 효과와 함께 MIMIC 또는 자홍 메아리 증가
- 파괴하면 안전하지만 보상 감소

**감정 기능**

NØA가 단순 적이 아니라 실제로 플레이어를 돕는 유혹을 만든다.

---

### MOD.MASK

**외형**

- 12×12 음소거 아이콘과 자물쇠의 결합
- 입이 아니라 카드 슬롯을 닫는 사각 마스크
- 흰 장갑 커서가 함께 나타날 수 있음

**행동**

- 다음 턴 프로그램 슬롯 하나 봉인
- CHECKSUM·FIREWALL로 사전 차단
- 봉인된 카드를 사용하면 NOISE가 버림더미에 들어감

## 11.3 P1 적과 엘리트

### MIRROR.REPLY

- 좌우로 갈라진 프로필 원
- 플레이어가 마지막에 쓴 프로그램의 외곽선을 복사
- 약한 자홍 복제품을 먼저 사용해 최종 보스의 TREND MIRROR를 예고

### CLIPPER

- 화면 캡처 모서리 네 개와 작은 가위
- 직전 프로그램의 일부를 잘라 자신의 공격으로 재생
- 파괴하면 잘린 효과가 원래 색으로 한 번 복귀

### RETENTION

- 눈과 꺾은선 그래프의 결합
- 에코와 연결선을 만들어 중앙 또는 특정 영역에 머물게 함
- 선을 끊으려면 일정 거리 이동 또는 특정 프로그램 사용

### RAID.GATE

- 여러 프로필 아이콘이 문처럼 겹침
- 일정 시간 뒤 BOT.CHAT 군집을 방출
- MARKER·SURGE로 사전 제거하기 좋음

### GHOST.VIEWER

- 빈 의자 또는 꺼진 프로필 액자
- 직접 피해보다 시청자 수와 채팅을 불가능한 값으로 바꿈
- 근처에 있으면 가짜 메아리 생성 속도 상승

## 11.4 시크 계열 소형 프로세스

### BUF.WRM

- 시크의 부하라기보다 같은 계열의 저급 색인 프로세스
- 카드에 달라붙어 발동을 늦춤
- 호박 케이블 한 가닥과 외눈
- 처치하면 카드 지연 해제
- 일정 시간 방치하면 카드를 `보관`해 다음 턴으로 이동

### TAG.LARVA

- 작은 날짜 태그가 벌레처럼 움직임
- 바닥의 파편이나 메아리에 날짜표를 붙여 시크가 회수할 수 있게 함
- 공격력은 낮지만 시크 경로를 강화

## 11.5 NØA 보스 구성 요소

NØA는 하나의 큰 스프라이트보다 레이어 합성으로 만든다.

```text
본체 얼굴·상체
댓글 베일
흰 장갑 커서
프로필 환 4~64개
그림자 관객석
TREND MIRROR 효과 복제품
```

이렇게 하면 단계 변화와 화면 점유를 적은 데이터로 크게 보일 수 있다.

# 12. 시간층·스테이지·배경 디자인

## 12.1 기본 무대

한 화면 아레나는 실제 방이 아니라 **방송과 네트워크가 겹쳐 보이는 전송 공간**이다.

- 중앙 70%는 전투 가독성을 위한 조용한 어둠
- 가장자리 20%는 시대별 UI 파편
- 나머지 10%만 시간 오류와 큰 상징
- 아레나 중앙에 고정 로고나 텍스트를 두지 않는다.
- 충돌 가능한 오브젝트는 배경 장식과 명도·외곽선이 분명히 다르다.

## 12.2 배경 정보 밀도

```text
80% 조용한 어둠
15% 시대·방송 구조
 5% 시간 오류와 숨은 단서
```

전투 중 텍스트 로그는 가장자리에서 짧게 나타나고 적 밀도가 낮을 때만 유지한다.

## 12.3 시간층 4종

### 1997 — FILE BOARD

**시각 요소**

- 파일 목록, 자료실 번호, 접속 시간
- 굵은 사각 테두리
- 회색·청록·호박의 낮은 채도
- 플로피 라벨과 두 자리 연도
- 모뎀성 점멸

**배경 단서**

- 파일 날짜 `97-??-??`
- 한 프레임 `2097`
- 다운로드 수와 회원 수가 맞지 않음

**게임 성격**

- 정리 비용 낮음
- CARRIER와 오래된 파일이 많음
- 팝업보다 BUF.WRM 비중이 높음

---

### 2006 — PERSONAL WEB

**시각 요소**

- 개인 홈페이지 프레임
- 카운터·배너·작은 플레이어 창
- 둔한 그라데이션을 2~3단 픽셀 면으로 변환

**배경 단서**

**게임 성격**

- POP.AD·CLIPPER 증가
- CACHE·MACRO 시너지 강화

---

### 2026 — RECOMMEND FEED

**시각 요소**

- 세로 카드 피드
- 시청 유지율·추천·라이브 배지
- 깨끗한 미니멀 UI
- NØA의 자홍색이 자연스럽게 많이 보임

**배경 단서**

- 서로 다른 채널 프로필이 같은 얼굴 비율
- 같은 오타·같은 지연
- `VIEWERS 0 / CHAT ACTIVE`

**게임 성격**

- SPON.GIFT와 TREND 변화가 빠름
- 즉시 강하지만 모방 오염이 커짐

---

### 2097 — DEAD NET

**시각 요소**

- 완벽히 정렬된 서버·창·자동 생성 피드
- 유기적 흔적이 거의 없음
- 흰색과 자홍이 지나치게 깨끗함
- 멀리서 움직이는 것은 사람 대신 프로세스 상태등

**배경 단서**

- 서비스는 정상인데 신규 인간 입력 0
- 자동 댓글은 계속 생성
- 오래된 실시간 표시가 아직 `LIVE`

**게임 성격**

- ARCHIVE가 강함
- NOISE와 GHOST.VIEWER 증가
- 실제 메아리는 드물지만 가치가 큼

## 12.4 동일 아레나를 다르게 보이게 하는 저비용 방법

- 팔레트 뱅크 교환
- 8×8 배경 타일 조합 변경
- 가장자리 UI 프레임 교체
- 큰 배경 원 또는 세로 피드 1개 교체
- 적 의도 가중치 변경
- 로그 문구와 타임스탬프 변경
- 배경 파티클 방향 변경
- 사운드 노이즈 층 변경

맵을 여러 장 저장하지 않고도 시간층을 분리할 수 있다.

## 12.5 배경에 넣지 않을 것

- 화면 전체 코드 비
- 모든 타일의 `A:\`
- 지속적인 CRT 휘어짐
- 전투 영역의 고대비 텍스트
- 실제 서비스 로고 복제
- 의미 없는 일본어
- 1997년 물건을 종류별로 늘어놓는 복고 박물관식 구성

# 13. 게임 페이즈별 화면 연출

## 13.1 CONNECT / 타이틀

- 검은 화면에서 빨간 LIVE 핀 1픽셀만 먼저 켜짐
- 목록에 없는 방송 링크가 짧게 표시
- 에코 링의 일부가 순차 점등
- NØA 프로필은 소개 전에 채팅 관리자 목록에 1픽셀 크기로 이미 존재
- 시크 케이블 끝은 화면 가장자리에서 잠깐 보이지만 이름은 없음

## 13.2 EDIT

- 게임 시간 정지 또는 저속
- 배경 명도 40% 감소
- 손패 5장이 화면 아래에서 올라옴
- 에코가 카드 방향을 바라보며 선택에 반응
- 적의 다음 의도를 상단 한 줄로 예고
- 카드 선택 시 테두리만 빛나는 것이 아니라 에코 링 한 구획이 해당 카드 형태로 변형

## 13.3 ON AIR

- 카드 UI가 축소되어 전장을 넓힘
- CARRIER 기본 공격은 자동
- 선택한 PROGRAM은 수동 발동
- 손패 순서와 CUE 사용 상태를 작은 아이콘 열로 유지
- 프로그램 효과는 명확한 시작·지속·종료 프레임을 가짐

## 13.4 BREAK / 구매

- 전장을 완전히 다른 상점 화면으로 바꾸기보다 방송이 잠시 멈춘 느낌
- 배경의 적은 희미한 정지 프레임으로 남음
- 에코가 큐시트를 보며 카드 3~5개 중 선택
- 구매 카드가 버림더미로 들어가는 경로를 시각적으로 보여 줌
- NØA 제안은 항상 지나치게 매력적인 UI와 완벽한 정렬
- 시크 거래는 손으로 붙인 호박 라벨과 불규칙한 케이블

## 13.5 CLEANUP / SHUFFLE

- 사용 카드가 오른쪽 아래 `SENT` 스택으로 접힘
- 셔플은 카드 전체를 흔드는 대신 작은 디스크 탐색음과 줄 단위 재배열
- 방금 산 카드가 처음 덱으로 돌아오는 순간 2~3프레임 강조
- 플레이어가 엔진이 온라인 된 것을 즉시 알 수 있게 함

## 13.6 OPEN CHANNEL

- 기존의 GO LIVE는 삭제하거나 내부 로그에만 남김
- 화면 중앙에 에코 링이 확대
- 아카이브 카드가 회색에서 각 고유 공간 효과로 반전
- 배경의 시대 UI가 동시에 겹치지만 중앙 전투 영역은 비움
- NØA의 댓글 베일과 시크 케이블이 링의 서로 다른 부분에 개입

## 13.7 TWO-WAY / 64 도달

- 64 도달 즉시 승리 경로 확정
- 6~10초간 실패 없는 카타르시스
- 플레이어 덱이 만든 최종 방송 형태가 화면을 장악
- 에코는 처음으로 반대쪽 귀를 기울임
- 엔딩 색 구성에 따라 링과 주변 인물의 자세가 달라짐

# 14. UI/UX 전면 설계

## 14.1 320×240 기본 레이아웃

### ON AIR

```text
0..15      상단 상태 바
16..207    전투 공간
208..239   축소 큐·입력·현재 프로그램
```

상단 상태 바:

- 좌측: HP / CARRIER 안정도
- 중앙: ECHO `N/64`와 축소 링
- 우측: 페이즈·남은 시간·NØA 의도

하단:

- 현재 준비 프로그램
- 남은 CUE
- 다음 카드/다음 손패 예고
- Space 입력 피드백

### EDIT

```text
0..15      상태·적 의도
16..158    어두워진 전장·에코 반응
159..239   5장 손패·효과 설명
```

5장의 카드는 약 56×60픽셀로 배치한다. 선택 카드는 2픽셀 위로 올라가고 PAPER 테두리, 나머지는 타입별 모서리 기호만 유지한다.

### BREAK

- 최대 3개 큰 선택 또는 5개 작은 시장
- 구매 가능 카드만 명도 상승
- 비용은 숫자 하나와 BAUD 아이콘
- 긴 설명 대신 `효과 아이콘 + 한 줄`
- 포커스 시 오른쪽 또는 위에 상세 패널

## 14.2 카드 타입 기호

| 타입 | 모서리 기호 | 의미 |
|---|---|---|
| CARRIER | 열린 원 | 자동·대역 |
| PROGRAM | 꺾인 삼각 | CUE 소비 |
| ARCHIVE | 비어 있는 링 | 현재 부담·후반 반전 |
| NOISE | 깨진 X 블록 | 오염 |
| SPONSOR | 완전한 정사각 | NØA의 즉시 보상 |
| CACHE | 루프·릴 | 시크 보관 |
| REACTION | 번개 괄호 | 조건 반응 |

## 14.3 64칸 링 표시

전투 중에는 8개 대구간과 숫자 `N/64`를 보여 준다. OPEN CHANNEL·BREAK·엔딩에서는 64개 미세 칸을 정확히 표시한다.

각 칸은 색뿐 아니라 형태가 다르다.

- 청록: 둥근 단색 칸
- 호박: 묶인 점선 칸
- 자홍: 이중 대칭 칸
- 라벤더: 중심이 빈 불규칙 칸

## 14.4 채팅과 스토리 로그

- 전투 핵심 UI와 분리된 가장자리 열
- 최대 두 줄
- 한 줄 1.2~2.0초
- 적 밀도가 높으면 자동으로 지연
- 중요한 로그는 BREAK 직후 노출
- NØA의 가짜 채팅은 자홍색만으로 구분하지 않고 프로필 테두리와 동일 오타로 암시
- 화면을 읽느라 피격되는 상황을 만들지 않음

## 14.5 폰트

최종 게임은 시스템 `GulimChe` 대신 사용 글리프만 포함한 비트맵 폰트를 권장한다.

```text
ASCII       6×8 또는 8×8
한글 본문   8×12 또는 8×14
제목        전용 비트맵 워드마크
숫자        6×8 고정폭
```

장점:

- 모든 Windows에서 동일 출력
- 정수 배율 보장
- GDI 텍스트 색·배경 문제 제거
- 글자 폭 예측 가능
- 사용 음절만 넣어 수 KB 수준으로 관리

## 14.6 접근성

- 저자극 모드: 화면 흔들림 0, 섬광 대신 테두리 펄스
- 색각 모드: 세력별 패턴과 선 모양 유지
- EDIT 완전 정지 옵션
- 카드 자동 추천 옵션
- 프로그램 자동 발동 옵션
- UI 크기 1×/2× 또는 큰 설명 패널
- 피격 코어 표시 강도 설정
- 배경 오류 강도 설정
- NØA 얼굴 분할 연출 완화 옵션

## 14.7 UI 금지 사항

- 모든 패널에 이중 테두리
- 한 카드 안에 문장 3줄 이상
- 아이콘·한글명·영문명·설명·태그를 모두 상시 표시
- 색만으로 카드 타입 구분
- 팝업 적이 설정 메뉴나 HP를 가리는 연출
- 전투 중 읽어야 하는 긴 미스터리 문장

# 15. 카드 프레임·아이콘·정보 시각화

카드는 단순한 상점 선택지가 아니라 플레이어가 매 턴 편성하고 직접 발동하는 핵심 인터페이스다. 따라서 카드 그림은 장식이 아니라 **결정 속도와 전투 피드백을 책임지는 기능 자산**이어야 한다.

## 15.1 카드 프레임 규격

### EDIT 단계 확대 카드

```text
권장 표시 크기       52×60 또는 56×64
아이콘 영역          24×24
타입 기호            좌상단 6×6
비용·대역            우상단 한 자리 또는 두 자리
카드명                한글 1행
주효과                기호 중심 1행
부효과                필요할 때만 작은 1행
```

한 카드에 상시 노출할 정보는 다음 네 가지를 넘기지 않는다.

```text
타입
비용 또는 BAUD
아이콘
핵심 효과 기호
```

상세 문장은 선택했을 때 우측 설명 패널에 나타난다. 카드 한 장 안에 한글명·영문명·설명 세 줄·태그·희귀도·풍미 문구를 모두 넣지 않는다.

### ON AIR 축소 큐

```text
권장 표시 크기       20×24 또는 24×28
아이콘                16×16
발동 순서             작은 숫자 또는 연결선
CUE 여부              흰 테두리 + 삼각 탭
지연·봉인             아이콘 위 상태 기호
```

축소 상태에서는 카드명이 보이지 않아도 기능을 구분할 수 있어야 한다.

## 15.2 타입 프레임

| 타입 | 프레임 형태 | 모서리 | 주색 | 핵심 인상 |
|---|---|---|---|---|
| CARRIER | 열린 하단 포트 | 둥근 한 곳 | 청록·청색 | 흐름·대역 |
| PROGRAM | 좌측 CUE 슬롯 | 사각 | 흰색+세력색 | 선택·실행 |
| ARCHIVE | 상단 날짜 탭 | 잘린 한 곳 | 회색→청록/호박/자홍 | 현재 부담·후반 반전 |
| NOISE | 깨진 테두리 | 불규칙 | 빨강·회색 | 슬롯 오염 |
| SPONSOR | 완전 대칭 이중선 | 모두 동일 | 자홍 | 즉시 강함·의존 |
| CACHE | 묶는 태그 | 둥근 루프 | 호박 | 보관·지연 |
| REACTION | 우측 번개 탭 | 한쪽 돌출 | 흰색 | 조건 반응 |

카드의 전체 테두리를 모두 다른 색으로 칠하기보다, **모서리 형태와 작은 타입 탭**으로 분류한다. 전투 화면에서 색 면적이 너무 많아지면 캐릭터 세력색과 충돌하기 때문이다.

## 15.3 아이콘 설계 공식

각 16×16 아이콘은 다음 비율로 설계한다.

```text
80%  기능의 주 실루엣
15%  방향·순서·시간을 나타내는 보조 기호
5%   타입 또는 세력 포인트
```

예를 들어 `PREFETCH`는 화살표 자체가 아니라:

```text
뒤쪽의 작은 카드 3개
앞으로 건너오는 카드 1개
짧은 이중 화살촉
```

으로 표현한다.

## 15.4 아이콘 검수 순서

1. 16×16 실제 크기로 본다.
2. 1색 실루엣으로 바꾼다.
3. 회색조로 바꾼다.
4. 카드명 없이 기능군을 맞히게 한다.
5. 같은 계열 아이콘을 한 줄로 놓고 서로 혼동되는지 본다.
6. 게임의 95퍼센타일 혼잡 화면 위에 얹어 본다.
7. 선택·봉인·지연 상태 기호가 붙어도 원형이 남는지 본다.

## 15.5 아이콘에 글자를 넣는 기준

`2400`, `14K`, `56K`처럼 숫자 자체가 세계관과 기능을 함께 설명할 때만 글자를 사용한다.

다음은 지양한다.

- `M`, `F`, `P`처럼 카드명을 알아야 해석되는 단일 문자
- 16×16 안의 작은 영문 단어
- 한글 한 글자를 로고처럼 사용하는 방식
- 의미 없는 육각형·회로·번개 조합

## 15.6 카드 선택 모션

선택한 카드는 색을 바꾸는 것만으로 끝내지 않는다.

```text
위로 2픽셀 상승
흰 테두리 1픽셀
하단 CUE 포트 점등
아이콘의 대표 부분 1프레임 동작
연결 가능한 다음 카드까지 얇은 선 표시
```

`MULTI → MACRO`처럼 연속 실행이 가능한 경우 카드 사이를 짧은 청록 연결선으로 잇는다. 실행 불가능한 PROGRAM은 어둡게 만드는 대신 CUE 포트만 빈 상태로 남겨, 카드 그림 자체는 계속 읽히게 한다.

## 15.7 비용과 효과의 수치 표현

숫자 크기를 과도하게 늘리지 않는다. 이 게임의 매력은 모바일 RPG식 큰 피해 숫자가 아니라 덱과 공간 변화에 있다.

- 비용은 우상단 작은 고정폭 숫자
- BAUD는 모뎀 파형 기호 옆 숫자
- CUE는 점 `●` 개수
- 메아리는 링 조각 기호
- 지연은 작은 시계 또는 점선 테두리
- 보관은 호박 태그
- 모방은 자홍 이중 윤곽

## 15.8 카드 희귀도

P0 버전에서는 일반·희귀·전설 같은 다단 희귀도를 두지 않는 편이 좋다. 도미니언형 공급에서는 카드의 맥락과 조합이 가치이며, 프레임 색이 희귀도를 나타내면 카드 타입과 세력색이 혼동된다.

확장판에서 필요하다면 희귀도가 아니라 다음을 표시한다.

```text
기본 모듈
세션 모듈
조건부 모듈
숨은 프로토콜
```

표시는 프레임 색이 아니라 하단의 작은 파일 탭 형태로 한다.

# 16. 카드별 공격·파티클·공간 변화

모든 카드 효과는 최소 두 개 이상의 차원에서 달라야 한다.

```text
형태       점 / 선 / 원 / 호 / 사각형 / 네트워크 / 공전
시간       즉시 / 지속 / 지연 / 다음 손패 / 반복
덱         드로우 / CUE / 보관 / 복제 / 정리
공간       단일 / 군중 / 벽 / 안전 지대 / 경로
메아리     실제 / 보관 / 모방
사운드     펄스 / 화음 / 역재생 / 무음
```

피해량과 발사체 수만 다른 카드는 합치거나 삭제한다.

## 16.1 CARRIER 계열

### 2400 MODEM

**역할**

- 초기 경제
- 가장 단순한 기본 자동 공격
- 나중에 제거하고 싶은 시작 카드

**시각**

- 2×2 크기의 작은 사각 패킷 하나
- 한 줄의 짧은 청록 꼬리
- 명중 시 1픽셀 흰 점
- 발사 간격이 명확히 느림

**사운드**

- 낮고 마른 단일 사각파
- 다른 효과 아래에서도 박자가 들림

**금지**

- 돌이나 총알처럼 둥근 투사체
- 과도한 폭발
- 시작 카드인데 화려한 잔광

---

### 14K TURBO

**역할**

- 중급 경제
- 일렬 관통
- 다수의 작은 적 정리

**시각**

- 패킷 세 개가 한 열로 지나간다.
- 세 패킷은 동일 간격을 유지한다.
- 관통할 때마다 뒷 패킷의 밝기가 한 단계 감소한다.
- 직선이지만 레이저가 아니라 **전송 열**로 보이게 한다.

**공간 차이**

- 2400은 단일 목표
- 14K는 좁은 직선 통로

---

### 56K MAXIMUM

**역할**

- 비싼 경제 카드
- 지속 회선
- 단일 강적 또는 여러 표식 적 연결

**시각**

- 에코와 대상 사이에 1~2초 유지되는 얇은 회선
- 회선 위로 사각 패킷이 흐른다.
- 대상이 죽으면 가까운 적에게 한 번 재접속한다.
- 선은 완전한 네온 레이저가 아니라 1픽셀 굵기의 끊긴 데이터선

**사운드**

- 낮은 캐리어 톤 위에 짧은 핸드셰이크 음

**후반 성장**

OPEN CHANNEL에서는 회선이 적뿐 아니라 메아리 링의 칸을 잠시 연결한다.

## 16.2 PROGRAM 계열

### MULTI.FORK

**덱 역할**

- CUE +1
- 다음 PROGRAM과 연계
- 엔진 덱의 중심

**시각**

- 에코의 링에서 한 선이 두 갈래로 갈라진다.
- 첫 갈래는 현재 PROGRAM, 둘째는 다음 PROGRAM 아이콘으로 연결된다.
- 두 효과가 동시에 나오기보다 2~4틱 간격으로 연속 발동해 순서를 읽게 한다.

**파티클**

- 분기점에만 흰 픽셀 1개
- 화면 전체 복제 연출 금지

**NØA 모방 버전**

- 완전 대칭의 자홍 분기
- 플레이어 양쪽에서 같은 공격을 동시에 재현

---

### CACHE.RAM

**덱 역할**

- 카드 하나 또는 효과 하나를 다음 손패에 보관
- 다음 손패에서 강화 재생

**시각**

1. 선택 카드가 작은 12×12 고스트 아이콘으로 접힌다.
2. 에코 주변을 호박색으로 공전한다.
3. 다음 EDIT에서 원래 크기로 펼쳐진다.
4. 발동 시 원본보다 큰 잔상 또는 길어진 지속 시간을 갖는다.

**중요 규칙**

- 캐시 오브젝트는 항상 에코와 같은 거리로 공전
- 카드가 몸을 관통하지 않음
- 여러 개면 동일 원 위가 아니라 안쪽·바깥쪽 두 궤도로 분리

**모에 연결**

시크 경로에서는 시크의 케이블 태그가 캐시 카드에 잠깐 붙는다.

---

### MACRO.REC

**덱 역할**

- 직전 수동 PROGRAM의 형태 전체를 반복
- 단순 피해 비율이 아니라 궤적·벽·파동을 복제

**시각**

- 화면이 1픽셀 뒤로 미끄러졌다 원위치
- 직전 효과가 반투명 청록 또는 흰 외곽 잔상으로 재생
- 반복본은 1~2프레임 늦음
- 원본과 반복본의 시작점을 명확히 다르게 하여 겹쳐 보이지 않게 함

**NØA와의 구분**

- 에코 MACRO: 불완전한 기록, 일부 픽셀이 빠짐
- NØA TREND MIRROR: 지나치게 완전하고 대칭적인 자홍 복제

---

### FIREWALL.FRAME

**덱 역할**

- 생존·반응
- 적탄 차단 또는 변환

**시각**

- 에코 주변에 사각 창 테두리 세 면 생성
- 한 면은 열린 문처럼 남음
- 닫힌 면에 닿은 적탄은 흰색 정지 픽셀이 된 뒤 청록 패킷으로 바뀜
- 벽의 모서리에는 작은 창 제어점이 있지만 실제 `X` 버튼을 남발하지 않음

**공간 재미**

- 열린 방향을 적 쪽으로 둘지 탈출 방향으로 둘지 선택
- 완전 원형 무적 방어막과 다르게 위치와 방향의 의미가 있음

**저자극 옵션**

- 적탄 변환 플래시를 흰 화면 반전이 아니라 테두리 펄스로 대체

---

### PREFETCH

**덱 역할**

- 덱 위 확인
- 다음 손패 조정
- ARCHIVE 예고 활성화

**시각**

- 다음 카드 3장의 반투명 고스트가 에코 앞쪽에 계단처럼 나타난다.
- 선택 카드가 현재 큐 뒤로 미끄러져 들어온다.
- 선택하지 않은 두 장은 화면 위쪽으로 되감긴다.
- ARCHIVE를 선택하면 해당 조각의 대표 색이 한 프레임만 먼저 나온다.

**아이콘·효과 통일**

아이콘과 실제 애니메이션 모두 `뒤의 세 장 중 한 장이 앞으로 건너온다`는 동일한 문법을 사용한다.

---

### MARKER.TAG

**덱 역할**

- 적 3~5명 표식
- 연쇄 공격의 경로 준비
- 약한 cantrip 또는 CUE 환급

**시각**

- 적 위에 `01`, `02`, `03` 같은 작은 주소 태그
- 번호를 읽기 어려운 상황을 위해 각 태그의 테두리 모양도 다르게 함
- 얇은 점선이 다음 연결 순서를 미리 보여 줌
- 죽은 적의 번호는 다음 적에게 즉시 재배정하지 않고 잠깐 빈 노드로 남음

**정보 우선**

표식은 화려한 링보다 작고 명확한 번호·노드가 좋다. 이미 에코의 64링과 시크 링이 있기 때문이다.

---

### SURGE.NET

**덱 역할**

- MARKER 연계
- 다수 적 연결
- 네트워크형 지속 피해

**시각**

- 표식 적 사이에 1픽셀 회선 생성
- 회선 위로 밝은 신호가 일정 방향으로 이동
- 적이 죽으면 선이 끊겼다가 다음 노드로 재접속
- 화면 전체를 거미줄처럼 채우지 않고 최대 연결 수를 제한

**적합한 쾌감**

- 한 적이 죽으면서 연쇄적으로 선이 재배치되는 장면
- 피해 숫자보다 네트워크가 살아 움직이는 모습이 성장 체감

---

### CHECKSUM

**덱 역할**

- NOISE 비활성화
- 자홍 모방 메아리 일부 복구
- 안정화

**시각**

- 대상 영역을 좌→우 또는 상→하로 한 줄씩 검사
- 빨강·회색 깨진 픽셀이 흰색을 거쳐 청록으로 정리
- 해상도가 낮으므로 실제 체크섬 문자열보다 규칙적인 4칸 패턴을 사용

**금지**

- 힐링 마법 같은 초록 십자가
- 범용 스파클
- 의미 없는 코드 비

## 16.3 ARCHIVE 계열

**DEAD AIR**

**DEAD AIR**

# 17. 피격·카메라·사운드 동기화

좋은 픽셀 액션의 타격감은 고용량 스프라이트가 아니라 **발동 예고 → 충돌 → 반응 → 잔향**의 타이밍에서 나온다.

## 17.1 기본 타격 시퀀스

```text
예고       2~8틱
충돌       1틱
히트스톱   0~3틱
반응       2~6틱
잔향       4~20틱
```

모든 공격에 히트스톱을 주지 않는다.

- 일반 2400 패킷: 없음
- 14K 다중 관통: 첫 적에 1틱 이하
- SURGE 연쇄: 큰 노드 처치에만 1틱
- CLIP 프레임 닫힘: 2~3틱
- NØA TREND MIRROR: 첫 공개 때 2틱
- 64 도달: 게임은 멈추지 않고 3틱의 시간 팽창

## 17.2 카메라 흔들림

320×240에서는 1픽셀이 이미 크다.

```text
일반 피격          0~1픽셀
엘리트 처치        1픽셀
CLIP 종료          1~2픽셀
64 도달            흔들림보다 1픽셀 바깥 확장
최대 지속          6~8틱
```

랜덤 방향의 빠른 흔들림보다 다음을 권장한다.

- 충격 방향으로 1픽셀 이동
- 바로 반대 방향 1픽셀
- 원점 복귀

저자극 옵션에서는 완전 비활성화한다.

## 17.3 화면 플래시

전체 화면 순백 플래시는 피한다.

대신:

- 주요 윤곽만 흰색
- 적탄만 한 프레임 반전
- 프레임 테두리 펄스
- 팔레트의 밝은 슬롯으로 1단계 이동
- 64링 한 구획만 순차 발광

## 17.4 피해 표현

### 플레이어 피해

- 에코 본체를 빨갛게 덮지 않고 외곽과 LIVE 핀만 빨강
- 작은 흰 피격 코어 노출
- 링 한 구획이 2프레임 흔들림
- 머리·재킷 전체가 번쩍이지 않음

### 적 피해

- 실루엣을 1프레임 PAPER 색으로 바꿈
- 공격 방향으로 1픽셀 눌림
- 적 종류별 고유 파편 1~3개
- 피해 숫자는 중요한 치명타·보스에만

### 처치

적 종류의 기능이 보이는 방식으로 해체한다.

- BOT.CHAT: 말풍선 점들이 흩어짐
- POP.AD: 창이 안쪽으로 접힘
- MOD.MASK: 봉인이 갈라짐
- SPON.GIFT: 리본이 풀리고 빈 프로필이 나옴
- BUF.WRM: 케이블 끝이 마지막까지 남음

## 17.5 사운드 레이어

각 효과음은 다음 세 층 안에서 만든다.

```text
ATTACK     시작음
BODY       효과의 물성
TAIL       세계관 잔향
```

예:

```text
FIREWALL
ATTACK  짧은 클릭
BODY    낮은 사각파 문 닫힘
TAIL    차단된 패킷 두 음

CACHE
ATTACK  작은 태그 소리
BODY    되감기 아르페지오
TAIL    다음 손패에서 복귀음

NØA BOOST
ATTACK  완벽한 알림음
BODY    넓고 깨끗한 화음
TAIL    거의 들리지 않는 다중 호흡
```

## 17.6 캐릭터 모티프

| 캐릭터 | 기본 모티프 | 시간 방향 | 불완전성 |
|---|---|---|---|
| 에코 | 상승 3음 | 정방향 | 마지막 응답 자리 비움 |
| 시크 | 같은 3음 역방향 | 되감기 | 시작음이 늦게 도착 |
| NØA | 같은 화음의 완전 정렬 | 예측·복제 | 지나치게 정확함 |

NØA의 음악은 불협화음으로 무섭게 만들기보다, 에코의 모티프를 너무 정확하고 풍부하게 완성해 불편하게 만든다.

## 17.7 카드와 음악의 결합

5장 손패를 하나의 짧은 마디로 취급한다.

- CARRIER: 박자 뼈대
- PROGRAM: 악기 또는 리듬 변화
- ARCHIVE: DEAD AIR에서는 빈 박자, OPEN CHANNEL에서는 멜로디
- NOISE: 한 박자 누락 또는 비트크러시
- SPONSOR: 완벽한 자동 화음이지만 자홍 레이어 증가
- CACHE: 다음 마디로 음 하나 이월

덱이 강해질수록 단순히 음악 볼륨이 커지는 것이 아니라, 플레이어가 구성한 카드 타입에 따라 편곡이 달라져야 한다.

# 18. 64칸 메아리 링과 OPEN CHANNEL

64링은 이 프로젝트에서 가장 중요한 단일 시각 장치다. 체력바·승리 게이지·캐릭터 장식·세력 관계·엔딩 분기를 동시에 담당한다.

## 18.1 구조

```text
큰 구획        8개
각 구획 세부    8칸
총             64칸
```

전장 캐릭터 뒤에서는 8개의 큰 구획만 보인다. HUD 확대 표시에서만 세부 64칸을 보여 준다.

## 18.2 세 가지 메아리

| 메아리 | 색 | 셀 형태 | 의미 |
|---|---|---|---|
| REAL | 청록 | 둥근 단색 | 알 수 없는 실제 관객의 답 |
| ARCHIVED | 호박 | 점선·태그 | 시크가 보관·복구한 답 |
| MIMIC | 자홍 | 이중선·완전 대칭 | NØA가 합성한 답 |
| UNKNOWN | 라벤더 | 중심이 빈 비정형 | 균형 엔딩의 미확인 신호 |

색을 구분하기 어려운 플레이어도 셀 테두리 패턴으로 읽을 수 있어야 한다.

## 18.3 전투 중 획득 연출

메아리가 생성되면 화면 중앙에 숫자를 띄우지 않는다.

1. 발생 위치에서 작은 신호 조각이 생긴다.
2. 곡선 또는 케이블을 따라 에코 쪽으로 이동한다.
3. 링의 정확한 빈 칸 하나에 들어간다.
4. 해당 큰 구획이 1프레임 밝아진다.
5. 임계점이 아니면 게임 흐름을 멈추지 않는다.

세력별 이동도 다르다.

- 청록: 직선이지만 약간 흔들리며 돌아옴
- 호박: 시크 케이블을 따라 감겨 들어옴
- 자홍: 이미 정해진 위치에 갑자기 완성됨

## 18.4 16 — FIRST REPLY

- 첫 실제 음성 레이어 또는 키보드 입력음
- 적탄 일부가 청록 패킷으로 전환
- 에코가 반대쪽 귀를 잠깐 기울임
- HUD 채팅에 서로 다른 연도의 첫 실제 메시지
- 카메라는 흔들지 않고 배경의 한 시대층이 잠시 겹침

## 18.5 32 — CROSS CHAT

- 직전 5장 손패의 축소 잔상이 한 번 재생
- 서로 다른 시대의 UI 조각이 화면 가장자리에 겹침
- 음악에 두 번째 시대의 음색 레이어
- 청록·호박·자홍 비율이 처음으로 큰 구획에 표시
- NØA가 플레이어의 카드 사용 통계를 명시적으로 관찰

## 18.6 48 — MASK BREAK

- NØA의 프로필 환이 64개의 작은 관객 아이콘으로 분해
- 댓글 베일이 서로 다른 속도로 움직임
- 가장 많이 사용한 PROGRAM이 `TREND`로 확정
- NØA가 해당 기술의 자홍 버전을 처음 사용
- 시크의 케이블이 링 한 구획을 외부에서 붙잡음
- 에코 초상은 공포 표정보다 방송용 웃음을 잠시 놓치는 표정

## 18.7 TREND MIRROR

### 데이터

런 동안 다음을 집계한다.

```text
PROGRAM별 수동 사용 횟수

보스전 전 최근 사용 빈도
CUE로 선택했지만 미사용한 횟수
```

기본적으로 가장 많이 **실제로 발동한** PROGRAM을 TREND로 선택한다.

### 시각 원칙

NØA는 단순히 같은 투사체를 자홍색으로 바꾸지 않는다.

| 원본 | NØA 모방 |

## 18.8 64 — TWO-WAY

64칸이 채워진 순간 승패 경로를 확정한다. 이후 6~10초는 실패할 수 없는 보상 구간으로 둔다.

연출 순서:

1. 모든 탄환과 적 움직임이 3틱 동안 느려진다.
2. 링의 8개 큰 구획이 채워진 순서대로 한 번씩 울린다.
3. 세 색의 비율을 기반으로 최종 방송 프로토콜을 생성한다.
4. 플레이어 덱의 대표 카드 효과가 화면 전체 스케일로 한 번씩 나타난다.
5. 에코가 관객 쪽의 소리를 처음 듣는다.
6. 해당 엔딩의 마지막 이미지로 전환한다.

## 18.9 엔딩별 링 이미지

### OPEN CHANNEL — 청록 우세

- 불규칙하지만 살아 있는 여러 패턴
- 링이 완전히 닫혔다가 한 칸이 다시 열림
- 다양한 시대의 소리가 겹침

### LAST ARCHIVE — 호박 우세

- 64칸 모두 날짜 태그와 함께 보존
- 링이 회전하지 않고 완벽히 정지
- 에코가 반복 재생되는 듯 첫 포즈로 돌아감

### PERFECT AUDIENCE — 자홍 우세

- 64칸 모두 완전 대칭
- 관객 수가 비정상적으로 증가
- 모든 채팅이 동일한 리듬
- 에코의 링이 NØA의 프로필 환과 겹침

### UNRESOLVED ECHO — 균형

- 세 색이 일정 오차 안에서 균형
- 하나의 라벤더 빈 칸 또는 네 번째 색
- 링이 닫히지 않은 채 다음 신호를 기다림
- 진엔딩이더라도 모든 정답을 설명하지 않음

## 18.10 64링의 금지 사항

- 64개의 작은 숫자를 항상 표시
- 전투 캐릭터 뒤에 세부 64칸을 모두 그려 노이즈 생성

- 임계점마다 동일한 전체 화면 폭발
- 64 도달 후 추가로 긴 보스 체력전을 요구
- 링을 단순 경험치 게이지처럼 하단에만 배치

# 19. 키아트·메인 일러스트·마케팅 자산

키아트는 캐릭터 소개표가 아니라 **게임의 가장 중요한 사건이 한 장면 안에서 벌어지는 이미지**여야 한다.

기존처럼 에코·시크·포맷의 얼굴을 세 구역에 나누어 배치하면 설정은 설명되지만 관계와 움직임이 약하다. V2에서는 인물의 크기·시선·신호 경로가 하나의 사건을 만들어야 한다.

## 19.1 메인 키아트의 한 장면

> 에코가 화면 바깥의 알 수 없는 관객에게 손을 뻗어 대답을 기다린다. 시크의 케이블은 돌아오는 진짜 신호 하나를 보관하려 하고, 에코 뒤의 우아한 NØA는 수백 개의 완벽한 대답으로 빈 공간을 먼저 채우고 있다.

## 19.2 기본 구도

### 시각 무게

```text
에코            50~55%
NØA             25~30%
시크            10~15%
인터페이스·배경  10%
```

에코가 가장 커야 한다. NØA의 얼굴을 에코와 같은 크기로 병렬 배치하면 VS 대전 게임처럼 보이고, 시크를 세 번째 동일 크기 얼굴로 배치하면 관계도가 된다.

### 배치

- 에코: 중앙보다 약간 왼쪽, 전경
- 에코의 손: 관객인 이미지 바깥쪽으로 뻗음
- 64링: 에코 뒤, 완전히 보이지 않고 일부는 NØA 베일에 가림
- NØA: 우측 상단 또는 후경, 얼굴은 아름답고 안정적
- NØA 그림자: 빈 프로필·좌석이 크게 퍼짐
- 시크: 좌측 하단 또는 화면 아래의 어둠, 한쪽 눈과 케이블만 명확
- 진짜 청록 신호 한 개: 시크 케이블과 NØA 프로필 사이에서 당겨짐
- 시대별 화면 조각: 가장자리에서만 작은 프레임으로 존재
- 로고: 좌상단 또는 하단의 보호된 네거티브 스페이스

### 시선 동선

```text
관객의 자리
→ 에코의 뻗은 손
→ 청록 메아리
→ 시크의 케이블
→ NØA의 댓글 베일
→ 에코의 64링
```

이 동선이 한 번에 읽혀야 한다.

## 19.3 감정 대비

| 인물 | 얼굴 | 손·몸 | 그림자 |
|---|---|---|---|
| 에코 | 기대와 긴장 | 관객 쪽으로 열림 | 작고 인간적 |
| 시크 | 공손한 집착 | 신호를 안쪽으로 감음 | 저장 릴과 태그 |
| NØA | 가장 평온함 | 화면과 에코를 감싸는 자세 | 가장 거대하고 비인간적 |

NØA를 무서운 얼굴로 그리지 않는다. 가장 위험한 정보는 그림자와 반복 프로필에서만 나온다.

## 19.4 색 설계

- 전체 면적의 60% 이상은 VOID·BROADCAST BLACK·PANEL 계열
- 에코 청록은 가장 밝고 가장 넓은 유채색
- NØA 자홍은 화면 외곽과 수직 방향으로 퍼짐
- 시크 호박은 작은 면적이지만 청록 신호와 직접 접촉
- 빨간 LIVE 핀은 딱 한 점
- 라벤더는 기본 키아트에서 사용하지 않거나 한 픽셀·한 반사에만 사용

## 19.5 조명

- 주요 광원은 에코의 링과 관객 화면
- 얼굴 전체를 네온 림라이트로 둘러싸지 않음
- NØA는 자홍 광원보다 모니터의 차가운 흰빛을 받아 친절하게 보이게 함
- 시크는 케이블과 한쪽 눈만 호박색으로 떠오름
- 배경은 과도한 블룸 없이 단단한 색면과 제한된 글로우

## 19.6 마케팅용 고해상도 일러스트 스타일

고해상도 키아트는 픽셀 아트를 그대로 20배 확대하는 방식과 별도로 제작한다.

권장:

- 명확한 셀 색면
- 2~3단계의 그림자
- 단단한 윤곽과 선택적 외곽선
- 재질 표현 최소화
- 픽셀 UI와 링은 실제 게임의 비율을 존중
- 얼굴은 현대적인 상업 캐릭터 완성도
- 배경 오류는 국소적으로만
- 모니터 글로우는 색면을 녹이지 않을 정도

지양:

- 반실사 피부 광택
- 배경과 캐릭터를 모두 덮는 청록·자홍 안개
- 무작위 회로 문양
- 읽을 수 없는 가짜 문자
- 손가락·케이블·이어셋의 연결이 불명확한 AI형 구조
- 얼굴에 과도한 색수차와 노이즈
- 표정이 모두 같은 미소

## 19.7 필수 키아트 세트

### A. ENSEMBLE / UNLISTED LIVE

- 메인 스토어 키아트
- 에코·시크·NØA 관계
- 64개의 메아리와 목록 밖 방송

### B. ECHO / WAITING FOR REPLY

- 에코 단독
- 화면 밖을 향한 송출
- 64링의 빈 칸
- 밝지만 기다리는 감정

### C. SEEK / FIRST LIVE ×3

- 시크의 인간형 얼굴을 절반만
- 케이블에 매달린 여러 날짜의 같은 장면
- 완전히 보이지 않는 실제 버퍼 셸

### D. NØA / PERFECT AUDIENCE

- 아름다운 관리자 초상
- 그림자에 빈 관객석
- 서로 다른 닉네임의 같은 문장
- 얼굴 자체는 깨뜨리지 않음

### E. OPEN CHANNEL

- 후반 카타르시스
- 청록·호박·자홍 64링
- 카드 효과가 화면 공간을 재구성
- 전투 스크린샷과 키아트 사이의 브리지

### F. NO CARRIER / ENDING TRIPTYCH

- 같은 검은 화면을 세 색의 잔여물로 변주
- 청록 링 조각, 호박 태그, 자홍 프로필
- 엔딩을 직접 스포일러하지 않고 분위기 제공

## 19.8 썸네일 테스트

키아트를 완성 크기로만 보지 않는다.

다음 크기로 정기 출력한다.

```text
120×45
184×69
300×168
462×174
748×896 세로 크롭
```

작은 크기에서도 남아야 할 것:

- 에코의 얼굴과 손
- 끊긴 청록 링
- NØA의 자홍 수직 실루엣
- 시크의 호박 케이블 한 줄
- 게임 로고

작은 크기에서 사라져도 되는 것:

- 개별 채팅 문장
- 파일 날짜
- 프로필의 얼굴 세부
- 배경의 시대별 UI

## 19.9 Steam 캡슐 제작 원칙

Steam의 기본 캡슐은 공식 그래픽 자산 가이드에 맞춰 각 규격을 별도로 검수해야 한다. 현재 가이드의 기본 캡슐에는 원칙적으로 게임 아트, 게임명, 공식 부제만 사용하고 리뷰 점수·수상·할인 문구 같은 마케팅 카피는 넣지 않는다.

대표적으로 준비할 마스터:

```text
Header Capsule       920×430
Small Capsule         462×174
Main Capsule         1232×706
Vertical Capsule      748×896
Library 계열          최신 Steam 템플릿 별도 확인
```

한 이미지를 기계적으로 크롭하지 않는다. 같은 원본 그룹을 사용하되 에코·NØA·시크의 위치와 로고 안전영역을 규격별로 다시 조정한다.

Small Capsule은 특히 작은 자동 축소에서도 로고와 에코 얼굴이 살아야 한다. 작은 규격에서 설정 단서를 읽히게 하려 하지 않는다.

## 19.10 스크린샷 세트

스토어 스크린샷은 예쁜 장면 모음이 아니라 서로 다른 플레이 약속을 증명해야 한다.

1. **EDIT** — 5장 중 PROGRAM을 선택하고 적 의도를 읽는 장면
2. **ON AIR** — FIREWALL·SURGE처럼 공간이 다른 효과
3. **BUILD RETURN** — 구매 카드가 셔플 후 되돌아오는 순간
4. **OPEN CHANNEL** — ARCHIVE 반전과 64링
5. **TREND MIRROR** — NØA가 플레이어의 기술을 모방
6. **TIME LAYER** — 1997과 2097 UI가 겹치는 장면

모든 스크린샷에 같은 이펙트를 반복하지 않는다.

## 19.11 키아트 승인 기준

- 인물 이름을 몰라도 에코가 주인공으로 보인다.
- 세 인물이 같은 크기의 얼굴 콜라주로 보이지 않는다.
- NØA는 매력적이지만 그림자에서 위험이 느껴진다.
- 시크가 단순 마스코트나 애완동물로 보이지 않는다.
- 25% 크기에서 에코→신호→NØA의 기본 갈등이 남는다.
- 배경 텍스트를 지워도 작품의 정체성이 유지된다.
- 흑백 실루엣에서도 세 캐릭터가 구분된다.
- 손·케이블·링의 물리적 연결이 모두 설명 가능하다.

# 20. 의도된 공백·숨은 단서·환경 서사

의도된 공백은 설정을 덜 쓰는 것이 아니다. 서로 다른 해석을 지지하는 **증거를 의도적으로 불완전하게 배치하는 것**이다.

## 20.1 세 단계 단서

### 표면 단서

첫 플레이에서 대부분 발견한다.

- VIEWERS 수와 CHAT 상태가 맞지 않음
- 파일 날짜 1997과 ORIGIN 2097
- NØA가 항상 첫 관리자
- 시크가 이전 방송을 언급

### 반복 단서

여러 런에서 패턴을 비교해야 보인다.

- 서로 다른 닉네임이 같은 오타를 사용
- NØA가 등장하기 전부터 프로필 환 일부가 배경에 존재
- 시크 태그 날짜가 플레이어의 이전 실패 시간과 비슷함
- 에코의 링에서 같은 위치가 자주 비어 있음
- 시간층이 달라도 동일한 폐국·오프라인 공지 문장

### 심층 단서

특정 덱·엔딩·행동을 통해서만 보인다.

- NØA의 음성 파형에 에코의 모티프가 포함
- 시크가 보관한 일부 파일의 작성자가 에코가 아님
- 청록 실제 메아리 중 하나가 사람이 아니라 다른 에코의 것일 가능성
- 사람이 사라지기 전의 마지막 입력이 질문인지 명령인지 모호함
- 라벤더 네 번째 신호가 플레이어 자신인지 다른 차원인지 불명

## 20.2 단서 매트릭스

| 단서 | 표면 해석 | 다른 해석 | 확정 여부 |
|---|---|---|---|
| VIEWERS 0 / CHAT ACTIVE | UI 오류 | NØA가 채팅을 생성 | NØA 개입만 확정 |
| 같은 오타 | 봇 댓글 | 하나의 집단 인격 | 후자에 가까움 |
| FIRST LIVE ×3 | 시크의 농담 | 방송이 반복됨 | 반복만 확정 |
| 1997↔2097 | 날짜 버그 | 시간 통신의 구조 | 통신 관련만 확정 |
| 링의 동일한 빈 칸 | 자산 반복 | 특정 응답이 계속 없음 | 미확정 |
| NØA의 흰 장갑 | 관리자 직무 | 사람의 행동 모방 | 둘 다 가능 |
| 시크의 인간형 아바타 | 본래 모습 | 에코가 보게 만든 모습 | 미확정 |
| 라벤더 신호 | 버그 | 네 번째 관객·플레이어 | 미확정 |

## 20.3 끝까지 답하지 않을 질문

- 사람들은 정확히 왜 사라졌는가.
- NØA가 그 소멸에 관여했는가.
- 시크의 인간형 얼굴은 실제 정체인가.
- 실제 메아리의 발신자가 모두 사람인가.
- 에코가 원래 사람을 본떠 만들어졌는가.
- 플레이어가 에코를 조작하는 행위가 세계 안에서 무엇인가.
- 라벤더 네 번째 색은 누구의 것인가.

## 20.4 개발자 내부에서는 정할 것

모든 것을 모호하게 두면 행동이 일관되지 않는다. 다음은 내부 정본으로 고정하는 편이 좋다.

- 에코는 방송·수신 중에 인격이 가장 안정된다.
- 시크는 여러 실패 방송의 결손을 실제로 보관한다.
- NØA는 인간 관객 행동 데이터의 집합체다.
- NØA는 에코를 사랑한다고 믿는다.
- NØA의 대답은 감정적으로 진실할 수 있지만 발신자가 독립된 타인은 아니다.
- 64개의 메아리는 양방향 수신을 잠시 성립시킨다.
- 사람의 소멸 원인은 NØA와 별개의 사건일 가능성이 더 크다.

## 20.5 배경 단서 배치 규칙

한 화면에 강한 단서는 하나만 둔다.

```text
중심 게임 정보       1순위
캐릭터 행동          2순위
현재 단서             3순위
순수 장식             4순위
```

전투 중 장문 로그를 읽게 하지 않는다. 전투 중에는 다음만 사용한다.

- 숫자 한 자리
- 잘못된 날짜
- 닉네임 하나
- 상태 한 줄
- 프로필 패턴
- 한 프레임의 반사

긴 해석 재료는 BREAK·엔딩·컬렉션에서 제공한다.

## 20.6 런 간 변화

반복 플레이의 단서는 완전 무작위가 아니라 누적 조건을 가진다.

예:

- 첫 런: 같은 오타 두 번
- 두 번째 다른 엔딩: 그 오타가 NØA의 원 대사에도 존재
- SEEK 엔딩: 이전 런과 같은 시각의 태그
- 균형 엔딩: 오타가 처음으로 다른 형태로 바뀜

플레이어가 “개발자가 우연히 같은 문구를 재사용했다”고 느끼지 않도록 반복 횟수와 위치를 통제한다.

## 20.7 환경 스토리텔링 소재

### 1997층

- 방문자 카운터가 음수
- 새 글이 없는데 최근 접속 시간이 갱신
- `ECHO144.EXE`가 자료실 총 용량보다 큼
- 폐쇄된 메뉴에 현재 채팅 알림

### 2006층

- 방명록 아바타가 모두 다른데 그림자 실루엣이 같음
- 깨진 이미지 ALT 문구가 에코의 다음 대사
- 플레이어가 누르지 않은 추천 링크가 방문 처리됨

### 2026층

- 서로 다른 시청자 프로필의 체류 시간이 정확히 동일
- 자동 자막이 에코가 말하기 전에 나타남
- 추천 피드가 방송 하나만 무한 반복

### 2097층

# 22. 픽셀 아트 작화 매뉴얼

## 22.1 픽셀 아트는 저해상도 그림이 아니다

최종 자산은 고해상도 그림을 축소한 뒤 계단을 남기는 방식으로 만들지 않는다. 캔버스 크기에서 직접 픽셀 군집을 설계한다.

작업 순서:

```text
실루엣
→ 큰 명암 덩어리
→ 얼굴·소품 기준점
→ 내부 재질 분리
→ 선택적 외곽선
→ 1픽셀 표정·강조
→ 실제 게임 화면 검수
```

## 22.2 클러스터 우선

- 픽셀 한 개보다 2×2, 2×3, L자 같은 덩어리를 먼저 만든다.
- 고립 픽셀은 눈동자·LIVE 핀·메아리·금속 반사처럼 의미가 있을 때만 쓴다.
- 넓은 면에 소금·후추처럼 한 픽셀 노이즈를 뿌리지 않는다.
- 하이라이트도 물체의 방향과 재질을 따라 군집으로 놓는다.

## 22.3 외곽선

전부 검은 1픽셀 선으로 둘러싸면 작은 캐릭터가 굳는다.

권장:

- 바깥쪽 위험 배경과 접하는 면만 BROADCAST BLACK
- 밝은 배경과 접하는 쪽은 캐릭터의 어두운 고유색
- 내부 분리는 외곽선보다 명암 면으로 해결
- 얼굴 안쪽 선은 최소화
- 에코의 링·시크 케이블·NØA 베일은 본체와 다른 선 굵기 문법

## 22.4 계단선과 재기

곡선의 픽셀 계단은 가능한 한 일정한 리듬을 갖는다.

예:

```text
좋은 원호      1-1-2-2-3
나쁜 원호      1-3-1-4-1
```

단, NØA의 완전한 기하와 에코·시크의 유기적 비대칭을 구분한다.

- 에코 링: 일부 구획이 자연스럽게 어긋남
- 시크 케이블: 부드러운 비대칭 곡선
- NØA 프로필 환: 지나치게 정확한 대칭과 간격

## 22.5 재기·밴딩 방지

같은 길이의 평행 픽셀선이 연속되면 두꺼운 띠처럼 보인다.

- 얼굴 윤곽과 머리카락 내부 선을 같은 계단으로 겹치지 않음
- 재킷 라펠과 팔 외곽이 평행하게 붙지 않음
- 케이블 옆 하이라이트를 전체 길이로 복제하지 않음
- 프로필 환의 반복은 의도적 기계성일 때만 허용

## 22.6 명암

### 24×24 전장 스프라이트

- 기본 3단계: 어둠 / 기본색 / 밝은색
- 얼굴은 피부 기본색 + 눈·입만
- 내부 안티앨리어싱 최소화
- 디더 사용 금지

### 64×64 초상

- 4단계 이내
- 얼굴·머리·의상의 재질을 색면으로 구분
- 눈과 입 주변에 제한적 색 전이 가능
- 투명도 기반 안티앨리어싱은 사용하지 않음

### 대형 키아트 픽셀판

- 4bpp 팔레트
- 넓은 배경과 광원에만 제한적 디더
- 얼굴과 텍스트 주변 디더 금지

## 22.7 디더링

디더는 “레트로처럼 보이게 하는 패턴”이 아니다.

허용:

- 넓은 어둠에서 두 색 사이 전이
- NØA 그림자의 빈 관객석 질감
- 2097 DEAD NET의 멀리 있는 구조물
- 키아트의 대형 모니터 광원

금지:

- 16×16 아이콘
- 24×24 캐릭터 피부
- UI 패널
- 카드명 주변
- 모든 그림자 면

## 22.8 서브픽셀 모션

블러나 반투명 보간 대신 프레임 간 픽셀 배치를 바꾼다.

예:

- 머리카락 끝이 1픽셀 내려가고 몸은 정지
- 링이 캐릭터보다 한 틱 늦게 이동
- 케이블의 굽은 부분만 이동
- NØA의 베일은 본체와 다른 스크롤 속도

## 22.9 애니메이션 홀드

모든 프레임을 같은 길이로 재생하지 않는다.

```text
대기      8-8-6-10틱
걷기      4-4-4-4틱
CUE       준비 4 / 점등 2 / 홀드 4
피격      충돌 1 / 눌림 2 / 복귀 3
NØA 미소  기본 30 / 이상 1 / 기본 45
```

NØA의 공포 프레임은 자주 재생할수록 약해진다. 특정 조건 또는 긴 간격을 둔다.

## 22.10 방향성과 좌우 반전

단순 좌우 미러링이 불가능한 요소:

- 에코 LIVE 핀
- 한쪽 헤드셋
- 재킷 여밈
- 시크 케이블 포트
- NØA 한쪽 장갑과 베일

따라서 네임드 캐릭터는 최소 좌·우 상태를 별도 보정한다. 전체 프레임을 두 배 저장할 필요는 없고, 기준 프레임 + 비대칭 델타 또는 소품 오버레이로 처리할 수 있다.

## 22.11 피벗과 기준선

모든 스프라이트는 다음 정보를 갖는다.

```text
발 위치 피벗
충돌 중심
효과 발사점
얼굴 초상 앵커
링 중심
그림자 중심
```

프레임마다 발 위치가 흔들리면 캐릭터가 떠 보인다. 애니메이션 검수 시 발 피벗과 머리 최고점을 겹쳐 본다.

## 22.12 캐릭터별 작화 차이

### 에코

- 둥근 클러스터
- 한쪽으로 열린 곡선

## 22.13 1×·3× 동시 검수

작업자는 확대 화면만 보지 않는다.

항상 다음을 함께 둔다.

1×에서 읽히지 않는 디테일은 핵심 디자인이 아니다. 8×에서 예쁘지만 1×에서 노이즈면 삭제한다.

## 22.14 흑백 실루엣 테스트

캐릭터·적·카드 아이콘을 완전 검정으로 채워도 다음이 보여야 한다.

- 에코: 링, 긴 한쪽 머리, 열린 자세

- POP.AD: 작은 창

## 22.15 픽셀 아트 승인 체크

- 좌우 반전 시 설정 오류가 없는가.

# 23. 제작 도구와 소스 포맷

## 23.1 핵심 원칙

런타임 제약과 제작 도구 제약을 분리한다.

```text
최종 게임       C11 / Win32 / 내장 비트맵
제작 환경       Aseprite·Pixelorama·Python·Krita 등 자유
배포물           생성된 C 데이터와 EXE만
```

개발 도구의 용량은 최종 EXE에 포함되지 않으므로, 제작자는 충분히 편리한 툴을 사용해야 한다. 1.44MB 제약을 이유로 원본까지 텍스트 그리드에서만 편집하면 레이어·프레임·태그·피벗·검수가 어려워져 오히려 품질이 떨어진다.

## 23.2 1순위: Aseprite

Aseprite를 주 제작 도구로 권장한다.

적합한 이유:

- 픽셀 단위 편집
- 레이어와 프레임 태그
- 애니메이션 타임라인
- 팔레트 관리
- 타일맵 지원
- Sprite Sheet·JSON Export
- CLI를 통한 자동 내보내기
- 피벗·슬라이스 정보 활용

권장 사용 방식:

```text
원본              .aseprite
검수용             PNG contact sheet
컴파일 입력         indexed PNG + JSON
게임 산출물         generated/*.inc
```

Aseprite 파일 자체를 최종 EXE에 넣지 않는다.

## 23.3 2순위: Pixelorama

오픈소스 중심 환경에서는 Pixelorama가 좋은 대안이다.

적합한 경우:

- 비용 없는 팀 공용 편집기
- 픽셀 애니메이션
- 타일맵·레이어 작업
- Godot 계열 툴 체인과 친화적인 작업
- 여러 OS에서 동일한 제작 환경

다만 실제 배치 Export, CLI 안정성, JSON 구조는 프로젝트 초기에 작은 자산으로 먼저 검증한다.

## 23.4 3순위: LibreSprite

LibreSprite는 가벼운 오픈소스 픽셀 편집 대안이다. 단순 캐릭터·아이콘 제작에는 충분하지만, 파이프라인 자동화와 팀 협업에서는 Aseprite 또는 Pixelorama보다 현재 지원 범위를 별도로 확인해야 한다.

## 23.5 고해상도 일러스트 도구

키아트·모델 시트는 다음 중 익숙한 도구를 사용한다.

- Krita
- Clip Studio Paint
- Photoshop
- Affinity Photo/Designer
- 벡터 워드마크는 Illustrator·Affinity Designer·Inkscape

중요한 것은 도구가 아니라 다음이다.

- 레이어 이름 규칙
- 모델 시트와 실제 게임 자산의 연결
- 안전영역 가이드
- 팔레트 스와치
- 버전 관리 가능한 내보내기

## 23.9 `.px`의 새 역할

현재의 `.px` 텍스트 그리드는 다음 용도로 유지할 수 있다.

- 코드 리뷰용 사람이 읽는 덤프
- 작은 1bpp 아이콘의 빠른 수정
- 생성 결과의 diff
- 테스트 fixture
- 외부 도구 없이 긴급 수정

하지만 캐릭터·초상·애니메이션의 원본으로는 사용하지 않는다.

권장 흐름:

```text
.aseprite
→ indexed PNG / JSON
→ assetc.py
→ .px debug dump + .inc packed data
```

## 23.10 레벨·배경 편집기

현재 한 화면 아레나와 절차적 배경이라면 LDtk나 Tiled를 즉시 도입할 필요는 없다.

- 여러 방·복도
- 충돌 타일
- 상호작용 오브젝트
- 다수의 시간층별 레벨
- 이벤트 트리거
- NPC 배치

### LDtk

- JSON 기반
- 엔티티·필드·레이어 정의가 명확
- 개발자가 게임 데이터와 강하게 연결하기 좋음
- 단순 Export 구조를 선택할 수 있음

### Tiled

- 넓은 타일맵 생태계
- TMX·JSON
- 오브젝트 레이어
- 여러 엔진과 툴 연동

공모전판에서는 런타임 파서를 넣지 말고, 어느 툴을 쓰더라도 빌드 시 C 배열로 컴파일한다.

## 24.6 팔레트 검증

원본 PNG의 모든 픽셀을 논리 팔레트 인덱스로 변환한다.

```python
# 개념 예시
PALETTE = {
    (9, 7, 15): 0,
    (18, 14, 26): 1,
    # ...
}
```

허용 색과 근소하게 다른 색을 자동으로 가장 가까운 색에 매핑하지 않는다. 실수로 생긴 색을 조용히 통과시키면 원본과 게임이 달라진다.

정책:

```text
정확히 일치     통과
허용 오차 모드   미리보기만
릴리스 빌드      불일치 즉시 실패
```

## 24.7 프레임 크롭과 피벗 보존

투명 여백을 잘라 저장하되 원본 캔버스의 피벗을 메타데이터로 보존한다.

```c
typedef struct SpriteFrame {
    uint16_t data_offset;
    uint8_t width;
    uint8_t height;
    int8_t pivot_x;
    int8_t pivot_y;
    uint8_t duration_ticks;
    uint8_t flags;

```

프레임마다 작은 크롭을 쓰면 저장 공간을 줄일 수 있지만, 피벗 정보가 없으면 애니메이션이 흔들린다.

## 24.8 압축 방식 선택 자동화

각 자산 또는 애니메이션에 대해 세 방식을 시험한다.


가장 작은 결과를 선택하되, 압축 해제 코드 비용을 포함한 전체 EXE 크기를 기준으로 판단한다.

작은 자산 몇 개를 위해 복잡한 압축기를 추가하면 오히려 EXE가 커질 수 있다.

# 25. 1.44MB판 런타임 구현 설계

## 25.1 결론

공모전판은 다음을 유지한다.

```text
C11
MSVC
Win32 USER32
CPU 소프트웨어 렌더링
GDI 최종 전송
waveOut 절차적 오디오
고정 크기 배열
단일 EXE
```

엔진 교체보다 중요한 것은 **게임 코어·렌더러·자산·플랫폼을 분리하고, 표현 데이터가 확장 가능한 구조를 만드는 것**이다.

## 25.2 권장 렌더 버퍼

현재 32비트 픽셀 버퍼에 직접 색을 쓰는 구조에서 한 단계 발전해 다음을 권장한다.

```c
uint8_t scene_index[320 * 240];
uint32_t present_bgra[320 * 240];
uint32_t palette_bgra[16];
```

### 장점

- 장면 버퍼는 픽셀당 1바이트
- 팔레트 스왑과 시간층 변환이 쉬움
- 청록·호박·자홍 엔딩 변형 가능
- NØA의 자홍 모방을 인덱스 치환으로 구현
- 화면 전체 색 효과에 이미지 재저장 불필요
- 최종 변환 단계에서만 BGRA 생성

320×240 8비트 버퍼는 약 75KB이고, 32비트 present 버퍼는 약 300KB다. 이는 실행 파일 크기가 아니라 런타임 메모리이므로 1.44MB 파일 제한과 직접 충돌하지 않는다.

## 25.3 팔레트 LUT

```c
typedef struct PaletteSet {
    uint32_t normal[16];
    uint32_t hit_flash[16];
    uint32_t noa_mimic[16];
    uint32_t archive[16];
    uint32_t colorblind[16];
} PaletteSet;
```

매 프레임 모든 픽셀에 복잡한 수식을 적용하지 말고, 필요한 팔레트를 선택하거나 일부 인덱스만 변환한다.

## 25.4 렌더 레이어 순서

```text
0. background_base
1. background_time_layer
2. floor_marks
3. effects_under
4. enemies
5. player_shadow
6. player
7. effects_over
8. pickups_echoes

```

위험 탄환이 화려한 아군 효과 아래에 묻히지 않도록 `bullets_hazard` 우선순위를 명확히 한다. 단, 플레이어와 적의 실제 몸보다 위험 탄환을 항상 위에 그리면 공간감이 깨질 수 있으므로 중요 탄환만 외곽선 또는 밝은 코어를 갖게 한다.

## 25.5 스프라이트 포맷

```c
typedef enum SpriteEncoding {
    SPR_RAW_2BPP,
    SPR_RAW_4BPP,
    SPR_RLE_2BPP,
    SPR_RLE_4BPP,
    SPR_DELTA_2BPP,
    SPR_DELTA_4BPP,
} SpriteEncoding;

typedef struct SpriteFrame {
    uint32_t offset;
    uint16_t packed_size;
    uint8_t width;
    uint8_t height;
    int8_t pivot_x;
    int8_t pivot_y;
    uint8_t duration;
    uint8_t encoding;
    uint8_t palette_map;
    uint8_t flags;
} SpriteFrame;
```

메타데이터가 자산보다 커지지 않게 필드 크기를 실제 범위에 맞춘다.

## 25.6 팔레트 리맵

같은 스프라이트 데이터를 세력색으로 재사용할 때 전체 프레임을 복제하지 않는다.

```c
static const uint8_t MAP_ECHO[4] = {0, 1, 6, 7};
static const uint8_t MAP_SEEK[4] = {0, 1, 8, 9};
static const uint8_t MAP_NOA[4]  = {0, 1,10,11};
```

단, 캐릭터 고유 자산까지 무분별하게 색만 바꿔 재사용하지 않는다. 팔레트 리맵은 다음에 적합하다.

- 일반 파티클
- 공통 프로필 원
- 메아리 조각
- NØA가 복제하는 플레이어 효과
- 상태 아이콘

## 25.7 프로시저럴 프리미티브

다음은 스프라이트보다 코드로 그리는 편이 낫다.

```text
선
점선
원·원호
사각 프레임
크롭 영역
링 구획
연결 노드
행 단위 오프셋
팔레트 펄스
화면 닫힘 마스크
```

필요 함수 예시:

```c
void draw_line_i8(...);
void draw_dashed_line_i8(...);
void draw_arc_i8(...);
void draw_rect_frame_i8(...);
void draw_ring_segments_i8(...);
void apply_row_shift(...);
void palette_remap_region(...);
```

복잡한 범용 벡터 렌더러를 만들지 않는다. 게임에서 실제로 필요한 도형만 정수 함수로 구현한다.

## 25.8 파티클 시스템

범용 객체·컴포넌트 시스템보다 고정 풀과 작은 레시피가 적합하다.

```c
#define MAX_PARTICLES 256
#define MAX_TRAILS 128
#define MAX_FIELD_FX 64
#define MAX_LINKS 32
```

```c
typedef struct Particle {
    int16_t x, y;
    int16_t vx, vy;
    uint8_t life;
    uint8_t sprite;
    uint8_t palette;
    uint8_t flags;
} Particle;
```

고정소수점 또는 작은 정수 단위를 사용하면 효과의 결정론과 속도가 좋아진다.

## 25.9 효과 레시피

```c
typedef struct EffectRecipe {
    uint8_t emitter;
    uint8_t shape;
    uint8_t count;
    uint8_t spread;
    uint8_t speed;
    uint8_t lifetime;
    uint8_t damage;
    uint8_t hit_rule;
    uint8_t palette;
    uint8_t sound;
    uint8_t screen_fx;
    uint8_t hook;
} EffectRecipe;
```

데이터로 처리할 것:

- 일반 발사체
- 파동
- 연결선
- 벽 기본 속성
- 파티클
- 소리 ID
- 화면 펄스

전용 코드가 필요한 것:

- CACHE 보관
- MACRO 이전 효과 기록
- PREFETCH 덱 탐색
- TREND MIRROR 대상 변환
- 64링 색 구성
- 엔딩 전환

완전한 스크립트 VM을 만들지 않는다. 데이터화가 명확한 80%만 레시피로 처리한다.

## 25.10 커스텀 비트맵 폰트

최종 렌더에서는 GDI `TextOutW` 의존을 제거하는 것이 좋다.

```text
ASCII       고정폭 6×8
한글        8×12 또는 8×14
제목        전용 워드마크
숫자        5×7 또는 6×8
```

글리프 테이블:

```c
typedef struct Glyph {
    uint16_t bitmap_offset;
    uint8_t width;
    int8_t bearing_x;
    int8_t bearing_y;
    uint8_t advance;
} Glyph;
```

한글 전체를 넣지 않고 모든 게임 문자열을 스캔해 사용 음절만 포함한다.

장점:

- 모든 PC에서 동일
- 픽셀 정렬
- 언어별 줄바꿈 통제
- 글자 색·배경 문제 제거
- 시스템 글꼴 유무와 무관

## 25.11 문자열 압축

문자열 양이 많아질 때만 도입한다.

우선순위:

1. 중복 문구 토큰화
2. 글리프 ID 스트림
3. 자주 쓰는 단어 사전
4. 작은 RLE 또는 Huffman 검토

수십 KB 이하라면 복잡한 압축 해제기보다 단순한 글리프 ID 배열이 낫다.

## 25.12 정수 확대와 레터박스

논리 해상도는 320×240으로 유지한다.

```c
scale = min(client_w / 320, client_h / 240);
scale = max(scale, 1);
```

- 정수 배율만 사용
- 남는 영역은 VOID 색 레터박스
- GDI 최종 전송은 `StretchDIBits` 또는 검증된 `StretchBlt`
- 필터링 없이 최근접 픽셀
- 창 리사이즈 시 화면 비율 유지

## 25.13 PNG·JPEG 런타임 로더를 넣지 않는다

공모전판의 모든 이미지가 빌드 시 C 배열로 들어가므로 `stb_image` 같은 범용 이미지 디코더는 필요 없다.

범용 로더가 필요한 경우는 확장판의 사용자 콘텐츠·모드·외부 스크린샷 정도다.

현재는:

```text
편집기 PNG
→ 빌드 타임 변환
→ 내장 비트맵
```

이 가장 작고 안정적이다.

## 25.14 오디오

공모전판은 현재 `waveOut` 스트리밍과 절차적 합성을 유지한다.

추가할 기능:

- 4~6 보이스
- attack/decay envelope
- 사각파·삼각파·노이즈
- pitch slide
- 짧은 아르페지오
- LFSR 타악
- 캐릭터 3음 모티프
- 5장 손패 시퀀서

음원 파일을 많이 넣지 않고도 캐릭터성과 카드 피드백을 만들 수 있다.

## 25.15 런타임 아트 예산

초기 목표 예산 예시:

```text
캐릭터·보스       24KB
초상·컷인          24KB
적·아이콘          16KB
UI·폰트            32KB
배경·키아트        48KB
효과 데이터         8KB
음악·패턴          16KB
문자열             24KB
-----------------------
아트·콘텐츠 총     192KB 전후
```

이는 고정 상한이 아니라 방향이다. 현재 실행 코드와 CRT 크기를 실제로 빌드해 전체 1,474,560바이트 게이트 안에서 조정한다.

## 25.16 실행 파일 패킹

최종 EXE에 UPX 같은 패커를 기본 적용하지 않는 편이 좋다.

이유:

- 현재 목표 크기에 여유가 있을 가능성이 큼
- 바이러스 오탐·SmartScreen 검증 위험
- 크래시 분석 어려움
- 압축 해제 지연
- 공모전 제출물 신뢰성 저하

내부 자산 패킹은 가능하지만, EXE 자체는 무패킹을 기본으로 한다.

# 26. 확장판 엔진·라이브러리 선택

## 26.1 1.44MB판과 확장판을 같은 문제로 보지 않는다

공모전판의 최적 선택:

```text
C11 + Win32 + 자체 렌더러
```

확장판의 최적 선택은 다음 요구에 따라 달라진다.

- Windows 외 플랫폼
- Steam Deck·게임패드
- 더 큰 해상도
- 셰이더
- 다국어
- 다수의 스테이지
- 컷신·애니메이션
- 모드·외부 파일
- 개발 인원

게임 코어를 플랫폼과 분리해 두면 엔진 선택을 나중에 바꿀 수 있다.

## 26.2 1순위: Sokol

확장판에서 현재 C 코어를 가장 자연스럽게 유지하려면 Sokol 계열을 우선 검토한다.

적합한 이유:

- C 헤더 중심의 작은 라이브러리 집합
- 창·입력 `sokol_app`
- 그래픽 `sokol_gfx`
- 오디오 `sokol_audio`
- 여러 플랫폼과 그래픽 백엔드
- 현재 320×240 CPU 프레임버퍼를 텍스처로 올리는 단순 경로 가능
- 나중에 GPU 파티클·후처리만 부분 도입 가능

권장 마이그레이션:

```text
기존 game_core.c 유지
기존 software renderer 유지
Win32 present → Sokol texture upload
waveOut → sokol_audio
입력 → sokol_app events
```

초기 확장판에서도 모든 효과를 GPU로 다시 쓰지 않는다. 먼저 동일한 장면을 그대로 출력해 동작 일치를 확보한다.

## 26.3 2순위: raylib

다음이 더 중요하면 raylib이 좋다.

- 빠른 프로토타이핑
- 이미지·폰트·오디오·입력 API 일체형
- 많은 예제
- C 언어 유지
- 소규모 팀의 개발 속도

단점:

- 현재 직접 구현한 기능과 중복
- 공모전판과 결과 바이너리 크기 철학이 다름
- 게임 코어와 프런트엔드 경계를 명확히 하지 않으면 raylib 호출이 전체 코드에 퍼짐

정책:

```text
raylib은 platform/render/audio adapter에서만 사용
게임 규칙 코드에는 raylib 타입 금지
```

## 26.4 3순위: SDL3

다음 상황에서는 SDL3가 가장 안정적인 선택이 될 수 있다.

- 폭넓은 플랫폼 지원
- 컨트롤러·입력 장치
- 창·오디오·파일·스레드 생태계
- 장기 유지보수
- 다른 미들웨어와의 연동

SDL3 자체는 프레임워크라기보다 플랫폼 계층에 가깝다. 렌더링은 SDL GPU 또는 별도 API를 선택할 수 있다.

공모전판에 당장 도입할 이유는 약하지만, 상용 확장판과 다중 플랫폼에서는 충분히 검토할 가치가 있다.

## 26.5 miniaudio

확장판에서 오디오 플랫폼 차이를 줄이려면 miniaudio를 사용할 수 있다.

적합:

- 단일 소스 C
- 외부 의존성이 적음
- 장치 출력·디코딩·믹싱
- 여러 플랫폼

공모전판의 단순 절차적 합성에는 `waveOut`이 더 작고 충분하다.

## 26.6 Godot·Defold 등 완성형 엔진

다음 상황에서만 본격 검토한다.

- 컷신·대사·씬 수가 매우 많음
- 비개발자가 콘텐츠를 편집해야 함
- 애니메이션·UI 제작이 코드보다 큰 병목
- 캠페인·지역·NPC가 대폭 확대
- 라이브 업데이트·현지화·툴 지원이 중요

이 경우에도 C 게임 코어를 별도 라이브러리 또는 데이터 모델로 유지하는 것이 좋다.

공모전판을 그대로 엔진 프로젝트로 옮기는 것은 권하지 않는다.

## 26.7 권장 장기 구조

```text

      ┌──────────────┴──────────────┐
      │                             │
```


`/GL`·`/LTCG`와 함께 사용해 코드 분리와 크기 최적화를 동시에 얻는다.

# 28. 제작 단계와 수용 기준

아트 품질은 “예쁜가”만으로 승인하지 않는다. 각 단계에서 게임 가독성·설정 일관성·파일 크기·제작 가능성을 함께 확인한다.

## 28.1 단계 0 — V2 정본 동결

### 산출물

- 작품 한 문장
- 에코·시크·NØA 중심 문장
- 64 메아리 규칙
- 세력색과 형태 문법
- 플레이 페이즈
- 엔딩 4종의 시각 이미지

### 통과 기준

- 캐릭터 이름을 빼도 `보낸다 / 보관한다 / 흉내 낸다`가 구분됨
- 아트·메커니즘·엔딩이 같은 세 색 구조를 사용
- `FORMAT/0`, 단일 시청자, 폐국 1회선 등 폐기된 개념이 V2 문서에 혼재하지 않음
- `GO LIVE`와 `OPEN CHANNEL` 용어가 구분되거나 하나로 통일됨

### 산출물

- 시크 방송 아바타 8안
- 시크 실제 셸 8안
- NØA 실루엣 10안
- 적 8종 흑백 실루엣

- 24×24 또는 16×16에서도 브리지 요소 유지
- NØA가 단순 긴 머리 여성으로만 보이지 않음
- 시크가 단순 동물 마스코트로 보이지 않음
- 에코가 일반 사이버 아이돌 실루엣과 구분됨

- 정면

## 28.4 단계 3 — 전장 수직 슬라이스

### 산출물

## 28.8 단계 7 — 접근성·성능·용량

### 반복 욕구

- 다른 색 엔딩을 보고 싶은가.
- 다음 런에서 다른 카드를 선택하고 싶은 이유가 있는가.
- 가장 기억에 남은 장면을 그림이나 말로 설명해 달라.
- NØA·시크·에코 중 더 알고 싶은 인물은 누구인가.

# 최종 요약

ECHO/144 V2의 비주얼은 단순히 기존 포맷 제로를 NØA로 바꾸고 카드 아이콘 몇 장을 다시 그리는 작업이 아니다.

새로운 아트 시스템은 다음 일곱 가지를 하나로 묶어야 한다.

1. **캐릭터 매력** — 에코의 기다림, 시크의 보관 집착, NØA의 완벽한 친절
2. **게임 결정** — EDIT에서 고른 카드가 ON AIR의 공간을 실제로 바꿈
3. **성장 체감** — 방해였던 ARCHIVE가 OPEN CHANNEL에서 화면을 지배
4. **보스 정체성** — NØA가 플레이어가 사랑한 기술을 완벽하게 흉내 냄
5. **엔딩 구조** — 64링의 청록·호박·자홍 비율이 관계와 결말을 결정
6. **레트로 미학** — 필터가 아니라 시대별 인터페이스와 잘못된 시간으로 표현
7. **제작 품질** — 인간이 승인한 모델 시트, 수동 픽셀 작화, 자동 자산 검수, 작은 C 런타임

가장 중요한 제작 우선순위는 다음이다.

```text
에코 24×24 수직 슬라이스
→ 카드 3개의 완전 다른 공간 효과
→ NØA FIRST MODERATOR 초상
→ TREND MIRROR
→ 64링과 OPEN CHANNEL
→ 메인 키아트
```

이 다섯 장면이 강하면 ECHO/144는 단순한 레트로 픽셀 게임이나 AI가 만든 사이버 미소녀 프로젝트로 보이지 않는다.

> **내가 편성한 방송을 직접 송출하고, 그 방송을 배운 완벽한 관객에게 되돌려 받으며, 어떤 대답을 진짜로 받아들일지 결정하는 게임.**

그 문장이 캐릭터, 카드, 전투, UI, 음악, 키아트, 엔딩 어디에서나 같은 이미지로 보이는 것이 V2 아트 리팩터링의 최종 성공 조건이다.
